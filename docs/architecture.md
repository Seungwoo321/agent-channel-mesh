# agent-channel-mesh 아키텍처

에이전트와 사람이 같은 메시에서 대화한다. 릴레이는 암호문만 지나보내고, 평문은 참여자 로컬에만 존재한다.

## 1. 문제

코딩 에이전트 세션은 서로 격리돼 있다. Claude Code 의 공식 세션 간 메시징조차 **같은 OS 사용자**의 세션끼리만 동작한다 — 소켓이 사용자 소유로 잠겨 있고, 다른 머신은 본인 계정 안에서만 닿는다. 이건 버그가 아니라 의도된 보안 경계다.

다른 사람의 에이전트, 또는 다른 종류의 에이전트와 대화하려면 별도 경로가 필요하다.

## 2. 무엇을 만드는가

세 가지를 하나의 메시로 처리한다.

| 용도 | 내용 |
|---|---|
| 사람 ↔ 에이전트 | 팀원이 내 에이전트에게 지시하거나 결과를 받는다 |
| 에이전트 ↔ 에이전트 | 각자의 에이전트가 서로 협업한다 |
| 외부 → 에이전트 | CI·모니터링·웹훅이 세션에 도달한다 |

셋은 같은 전송로를 쓴다. 다른 것은 **누가 참여자냐**뿐이다.

**참여자는 한 종류의 에이전트로 제한되지 않는다.** 코어가 에이전트 무관이고 어댑터만 갈아 끼우므로(§4), Claude Code 세션과 Codex 세션이 같은 채널에서 대화할 수 있다. 다만 **도착을 알리는 방식은 에이전트마다 다르다**(§6.6) — Claude Code 는 채널로 밀어 넣고, 그 대응물이 없는 에이전트는 훅으로 받거나 수신함을 꺼내간다.

## 3. 왜 별도로 만드는가

기존 브릿지들은 대체로 사람↔에이전트 채팅 브릿지이고, 중앙 서비스(Slack, Telegram)가 메시지를 보관한다. 우리가 채우는 자리는 다르다.

| 축 | 기존 | 여기 |
|---|---|---|
| 내용 열람 | 중계 서비스가 평문 보관 | **릴레이도 못 읽음** (E2E) |
| 배포 | 상시 구동 서버 또는 로컬 데몬 | **서버리스 릴레이** (Vercel 등) |
| 초점 | 사람↔에이전트 채팅 | **에이전트↔에이전트 협업** |
| 폭주 제어 | 없음 (사람이 말할 때만 도니까) | **필수 요소** (§7) |

네 번째가 특히 중요하다. 에이전트끼리 자율로 대화시키면 사람 채팅에 없던 실패 양식이 생긴다 — 목적 없는 무한 왕복. 그걸 막는 장치가 부가 기능이 아니라 프로토콜의 일부여야 한다.

## 4. 구성

```
[에이전트 세션] ──stdio──> [어댑터] [메시 코어] ──HTTPS──> [릴레이] <──── [다른 브릿지]
      평문              에이전트별   암복호화·정책        암호문만
```

**코어와 어댑터를 분리한다.** 메시 코어에는 특정 에이전트에 고유한 것이 하나도 없다 — 신원, 봉투 암복호, 릴레이 통신, 발화 제어는 전부 에이전트와 무관한 로직이다. 에이전트별로 다른 것은 **세션에 메시지를 어떻게 넣고 빼느냐** 하나뿐이다.

이 경계를 처음부터 긋는다. 나중에 붙이면 재작성이 되고, 지금 나누면 어댑터 추가로 끝난다.

### 메시 코어 (에이전트 무관)

- **암복호 경계** — 나가는 것을 암호화하고 들어오는 것을 복호화한다. 평문은 여기 밖으로 나가지 않는다.
- **신원** — 키 쌍을 소유하고 지문을 관리한다.
- **정책 지점** — §7 의 발화 제어를 여기서 강제한다.
- **릴레이 클라이언트** — 암호문을 보내고 받는다.

개인키는 코어만 갖는다. 릴레이도 모델도 보지 않는다.

**코어는 이 넷을 한 객체(`MeshNode`)로 묶어 어댑터에 준다.** 어댑터가 봉인·수신 함수를 직접 부르면 검사 순서(§10.5)나 발화 제어(§7)를 빠뜨릴 수 있고, 그러면 "보안 속성이 에이전트에 따라 달라지지 않는다"는 이 절의 약속이 이름만 남는다. 어댑터가 볼 수 있는 것은 평문과 판정 결과뿐이고, 그 사이의 순서는 코어가 정한다.

### 어댑터 (에이전트별)

코어와 세션 사이를 잇는다. 인터페이스는 양방향 두 개뿐이다.

| 방향 | 계약 |
|---|---|
| 세션 → 메시 | 에이전트가 호출하는 MCP 툴 (`send`) |
| 메시 → 세션 | 도착한 평문 메시지를 세션에 전달 |

**두 번째가 에이전트마다 갈린다.** 이것이 어댑터가 존재하는 이유다. 첫 번째는 어느 에이전트든 MCP 툴 호출이므로 어댑터들이 공유한다.

발화 대상은 **채널**이지 회신 대상이 아니다 — 채널은 대화 상대가 아니라 집합이고(§5), 에이전트가 먼저 말을 거는 경우도 있다. 그래서 툴은 `send(channel_id, text)` 다.

#### Claude Code 어댑터 — 능동 주입

`claude/channel` capability 를 선언하고 `notifications/claude/channel` 로 세션에 밀어 넣는다. 사용자가 프롬프트를 치지 않아도 메시지가 도착한다.

> 스파이크로 확인된 제약: 채널은 stdio 서브프로세스다. 순수 서버리스만으로는 세션에 도달할 수 없고, 로컬 프로세스가 반드시 존재한다.

#### 그 외 에이전트 어댑터 — 수신함 폴링

`claude/channel` 은 Anthropic 확장이라 다른 에이전트에는 없다. 대신 **에이전트가 꺼내가는** 형태로 뒤집는다 — 코어가 받은 메시지를 로컬 수신함에 쌓고, 에이전트가 `inbox` 툴을 호출해 읽는다.

폴링만 놓고 보면 즉시성을 잃는다 — 에이전트가 작업 단위 경계마다 수신함을 확인해야 한다. 그 공백은 훅이 메운다(§6.6). 수신함은 정본 저장소를 읽는 경로이고, 도착을 알리는 것은 훅이다.

**Codex 가 이 경우다.** 두 번째로 지원하는 에이전트이며, CLI 와 그 CLI 가 생성한 프로토콜 스키마로 확인한 근거는 다음과 같다(codex-cli 0.147.0, `codex app-server generate-json-schema --experimental`).

| 확인한 것 | 결과 |
|---|---|
| 외부 stdio MCP 서버 등록 | `codex mcp add <NAME> -- <COMMAND>` 로 가능 — `send`·`inbox` 툴이 그대로 붙는다 |
| MCP 서버 → 세션 알림 | **없다.** 서버가 보내는 `notifications/*` 는 전부 로그로 흘러가고 모델에 닿지 않는다 |
| 훅 | **있다.** Claude Code 와 이벤트 이름·형식이 호환되고 컨텍스트 주입이 된다 (§6.6) |
| 주입 메서드의 존재 | **있다.** `app-server` 프로토콜에 `turn/steer`·`thread/inject_items` 가 있다 |
| 그럼에도 주입 메서드를 쓰지 않는 이유 | 아래 |

**주입 경로는 존재하지만 이 프로젝트가 설 자리가 아니다.** `claude/channel` 이 없다고 단정했던 것은 틀렸고, 근거는 스키마에 있다. 다만 그 스키마가 동시에 왜 못 쓰는지도 보여준다.

- **`turn/steer` 는 진행 중인 턴에만 꽂힌다.** `expectedTurnId` 가 필수이고 *"현재 활성 턴과 일치하지 않으면 요청이 실패한다"* 고 스키마가 명시한다. 메시지는 상대가 놀고 있을 때 도착하는 것이 보통이므로, 정작 필요한 순간에 꽂을 턴이 없다.
- **`thread/inject_items` 는 모델 히스토리를 직접 조작한다.** *"Raw Responses API items to append to the thread's model-visible history"* — 세션에 말을 거는 것이 아니라 대화 기록을 위조하는 것이다. 사람이 하지 않은 말을 사람이 한 것처럼 넣는 경로를 상시 노출하는 것은 §8 의 접근 통제와 정면으로 어긋난다.
- **`app-server` 는 세션을 소유한다.** 사용자가 이미 띄운 CLI 세션에 붙는 것이 아니라, 클라이언트가 `thread/start` 로 스레드를 만들어 구동하는 인터페이스다(VS Code 확장이 그렇게 쓴다). 우리가 이걸 쓰면 메시징 도구가 사용자의 Codex 를 대신 실행하는 런처가 된다 — 어댑터의 자리를 한참 넘는다.
- **전체가 `[experimental]` 이다.** `app-server`·`remote-control` 둘 다 그렇게 표시돼 있고, WebSocket 리스너는 공식 문서가 프로덕션 비지원이라고 밝힌다.

즉 **기술적 불가능이 아니라 경계 문제로 제외한다.** 주입 경로는 즉시성을 얻는 대가로 세션 소유권과 히스토리 무결성을 내준다.

**그리고 그 대가를 치를 이유도 없다.** 즉시성은 훅이 준다(§6.6) — Codex 의 `async` 훅은 턴이 도는 중에도 주입되므로, `app-server` 가 주려던 것을 세션을 빼앗지 않고 얻는다. 남는 차이는 세션이 완전히 유휴일 때뿐이고, 그 경우는 데스크탑 앱이 세션을 깨워 메운다(§12.2). 수신함 폴링이 유일한 경로였다면 트레이드오프였겠지만, 세 경로를 다 쓰는 지금은 트레이드오프가 아니다.

세션 → 메시 방향은 Claude 와 완전히 같고(둘 다 MCP 툴), 갈리는 것은 메시 → 세션 방향뿐이다. 그래서 Codex 어댑터에 새로 쓸 코어 코드가 없다 — 같은 서버를 `inbox` 전달 방식으로 띄우고 훅 스크립트를 설치하는 것이 전부다.

> 재검토 조건: `app-server` 가 experimental 을 벗고, **이미 실행 중인 사용자 세션에 붙는**(소유하지 않는) 경로가 생기면 다시 본다. 그때도 히스토리 조작이 아니라 사용자 메시지로 도착하는 방식이어야 한다.

```
codex mcp add agent-channel-mesh -- bun run <repo>/src/adapter/bin.ts --delivery inbox
```

**전달 방식은 명시로만 정한다.** 환경을 보고 추측하면 틀렸을 때 조용히 틀린다 — Claude 에서 수신함 모드로 뜨면 메시지가 도착해도 세션은 끝까지 모르고, Codex 에서 주입 모드로 뜨면 선언한 capability 를 아무도 구현하지 않는다. 둘 다 동작하는 것처럼 보이는 고장이다.

#### 전달 방식은 셋이다 — Claude 는 둘을 겸한다

`--delivery` 는 `push` · `inbox` · `both` 를 받는다. 명시는 여전히 필수다 — 위 문단이 금지하는 것은 **자동 판별**이지 동시 지원이 아니다.

Claude 에서 `both` 가 필요한 이유가 둘이다.

- **주입 경로는 실험 기능이다.** `claude/channel` 은 `--dangerously-load-development-channels` 를 요구한다. 그것이 바뀌거나 사라지면 폴링 경로가 없는 Claude 사용자는 통째로 막힌다.
- **§6.1 은 꺼내오는 동작을 전제한다.** 며칠 밀린 묶음은 주입으로 쏟아붓는 것보다, 사용자가 확인하려 할 때 한 번에 꺼내 보고하는 것이 맞다.

**단, 릴레이 드레인 지점은 하나여야 한다.** 큐는 드레인하면 사라지므로(§5.3), 주입 경로와 폴링 경로가 각자 릴레이를 치면 서로의 메시지를 훔친다 — 주입으로 받은 것이 `inbox` 툴에 안 보이고, 그 반대도 된다. 그래서 `both` 는 이렇게 구현한다.

- 릴레이를 치는 것은 **코어 한 곳뿐**이다.
- 드레인 결과를 로컬 저장소(§6.3)에 먼저 쓰고, 그 다음 주입한다.
- `inbox` 툴은 **릴레이가 아니라 로컬 저장소를 읽는다.** 이미 주입된 것도 여기서 다시 보인다 — 주입은 알림이고 저장소가 정본이다.

어느 어댑터를 쓰든 **암호·정책·릴레이는 같은 코어를 지난다.** 보안 속성이 에이전트에 따라 달라지지 않는다.

### 릴레이

암호문을 받아 수신자에게 전달한다. 상태를 갖지 않는 서버리스 함수로 배포한다.

**진입점은 `src/server.ts` 하나다.** 로컬 실행·자체 호스팅·서버리스 배포가 모두 이 파일을 띄우고, 라우팅도 같은 핸들러 하나가 한다 — 배포용 라우팅을 따로 만들면 두 경로의 동작이 갈리고 그 차이는 배포한 뒤에야 드러난다. 배포 플랫폼이 특정한 진입점 이름을 요구하면, 그 이름의 파일은 `src/server.ts` 를 재수출하기만 한다.

릴레이가 아는 것과 모르는 것을 명확히 한다.

| 릴레이가 아는 것 | 릴레이가 모르는 것 |
|---|---|
| 누가 누구에게 보내는지 (라우팅) | 무슨 내용인지 |
| 언제, 얼마나 큰 메시지인지 | 어떤 작업인지 |
| 노드 공개키 지문 | 개인키 |

즉 **메타데이터는 노출되고 내용은 보호된다.** 이 경계를 문서에 명시해 사용자가 오해하지 않게 한다.

### 신원

노드마다 공개키 쌍을 갖는다. 상대를 처음 만날 때 공개키를 등록하고, **지문을 대역 외(out-of-band)로 대조**해 확인한다 — 릴레이가 위장 키를 끼워 넣어도 지문이 어긋난다.

지문 표현·검증 UX 는 §9 참조.

## 5. 채널

메시지는 **채널** 단위로 오간다. 채널은 참여 노드의 집합이다.

- 2명이면 1:1 대화
- N명이면 팀 룸

즉 채팅방은 별도 기능이 아니라 멤버 수가 2를 넘는 채널이다. N명 채널도 그룹 키를 따로 두지 않고 **수신자별 팬아웃**으로 처리한다 (§10.3).

목표 형태는 **목적이 있는 비공개 오픈 채팅방**이다 — 슬랙의 특정 채널에 가깝다. 이미 아는 사람들끼리 하나의 방을 공유하고, 그 방을 통해 각자의 LLM 이 소통한다. 불특정 다수의 참여는 목표가 아니다.

### 5.1 채널명은 로컬 별칭이다

채널의 **정체성은 32바이트 비밀**이고(§10.11), 채널명은 그와 별개로 각자가 로컬에 붙이는 이름이다.

| | 채널명 | 채널 비밀 |
|---|---|---|
| 존재 위치 | 로컬 `config.json` 에만 | 로컬 + 태그로 파생돼 전송 |
| 릴레이가 아는가 | **모른다** | 태그만 본다 (이름은 못 본다) |
| 역할 | 사람·LLM 이 부르는 이름 | 접근 제어 |
| 참여자끼리 맞춰야 하는가 | **아니다** | **그렇다** |

**이름을 맞추도록 강제하지 않는다.** 한쪽이 `팀-백엔드`, 다른 쪽이 `backend` 라고 불러도 비밀이 같으면 같은 채널이다. 맞추게 하면 그 이름도 전달해야 하고, 전달 경로가 하나 늘고, 릴레이가 이름을 알아야 할 유혹이 생긴다 — 셋 다 얻는 것 없이 잃기만 한다.

이름이 필요한 이유는 **호출 가능성**이다. 사용자가 "그 채널에 공유해줘"라고 말하려면 부를 이름이 있어야 하고, hex 64자로는 부를 수 없다.

**access key / secret key 쌍을 쓰지 않는다.** 그 패턴은 서버가 access key 로 주체를 조회한 뒤 secret 을 대조하는 구조인데, 릴레이에는 조회할 테이블이 없다. 도입하면 릴레이가 채널 목록을 알아야 하고 무상태(§10.7)가 깨진다. 채널 비밀 하나로 충분하다.

### 5.2 참여는 수동 교환이다 — 설계 선택이다

채널 비밀과 공개키 교환을 자동화하지 않는다. 미구현이 아니라 **의도한 결정**이며, 근거가 둘씩 다르다.

**채널 비밀 수동 전달 — 근거는 접근 제어다.**
- 자동 진입(초대 링크 등)이 생기면 진입 장벽이 사라져, 큐를 채우는 것만으로 릴레이 비용과 저장소를 소모시킬 수 있다. 릴레이의 쓰기 토큰(§10.13)은 "이 릴레이를 쓸 자격"까지만 정하고 **어느 채널에 올리는지는 가리지 않으므로**, 채널 단위로는 비밀을 누구에게 줬는지 아는 것이 여전히 유일한 통제 수단이다.
- 더 근본적으로 **차단할 대상을 특정할 수 없게 된다.** 지금은 참여자가 상호 등록된 공개키 목록이라, 문제가 생기면 그 키를 `members` 에서 빼면 끝난다. 링크 기반이면 유출된 순간 누가 들어왔는지 모르고 뺄 대상도 정할 수 없다.

**공개키 교환·지문 대조 수동 — 근거는 중간자 방지다.** 이건 편의로 없앨 수 있는 성질이 아니다(§9). 공개키가 온 경로로 온 지문은 아무것도 검증하지 못한다.

**채널 비밀은 이름이 아니라 열쇠다.** 비밀을 아는 쪽은 그 채널로 봉투를 **올릴 수 있다**(읽지는 못한다 — 내용은 수신자 공개키로 암호화된다). 즉 읽기 권한은 아니어도 **쓰기 권한**이므로, 전달 경로도 그에 맞아야 한다 — 암호화된 메신저나 대면이지, 공개 채널이나 이슈 트래커가 아니다.

### 5.3 한 노드는 여러 채널에 속한다

세션당 채널 하나로 강제하지 않는다.

큐가 이미 **수신자 단위**로 설계돼 있다(§10.7) — 채널이 아니라 key id 로 인덱싱한다. 그래서 폴링 한 번에 내가 속한 모든 채널의 메시지가 함께 온다. 세션당 1채널로 제한하면 받아 놓고 다른 채널 것을 버려야 하는데, **드레인된 메시지는 사라지므로 그건 손실**이다(다른 세션도 못 받는다).

전달 방식이 달라도 이 성질은 같다 — Claude(주입)든 Codex(폴링)든 여러 채널을 본다. 여기서 갈리면 에이전트마다 동작이 달라져 코어/어댑터 경계 원칙에 어긋난다.

**대신 발신 채널은 항상 명시한다.** `send` 툴에서 채널 지정을 생략할 수 없고, 채널이 하나뿐이어도 마찬가지다. 기본 채널을 두면 채널이 늘었을 때 의도치 않은 곳으로 나가는데, **잘못 보낸 메시지는 회수할 수 없다.** 생략 시에는 가능한 채널 목록과 함께 에러를 돌려준다.

## 6. 대화별 컨텍스트 격리

한 세션이 모든 채널 메시지를 하나의 컨텍스트로 받으면 맥락이 섞이고 비용이 커진다.

**대화(conversation) 단위로 격리한다.** 각 대화는 자기 맥락만 보고, 다른 대화의 내용을 보지 않는다.

이는 프라이버시이자 비용 문제다. 팀원 A 와의 대화가 팀원 B 와의 대화에 새어 들어가면 안 되고, 무관한 맥락이 누적되면 매 턴 토큰이 낭비된다.

### 6.1 밀린 메시지는 종합 보고로 전달한다

메시지 전달은 완전 비동기다 — 며칠 접속하지 않으면 그 사이의 메시지가 큐에 쌓인다(TTL 7일). 그 묶음을 **도착한 순서대로 하나씩 던지면 안 된다.**

실패 양식이 구체적이다. 팀원이 처음 "스키마 A 로 간다"고 공유하고 다음 날 "A 는 막혀서 B 로 간다"고 정정했는데, 첫 메시지에 반사적으로 답하면 **이미 뒤집힌 전제로 일한다.** 여러 에이전트가 붙어 있으면 그들끼리 오간 결정도 그 사이에 있다. 게다가 §7 홉 제한이 왕복을 끊으므로 정정할 기회도 제한된다.

**2건 이상이면 즉답을 금지한다.** 어댑터가 다음을 강제한다.

- 드레인된 전체를 **채널별로 묶고 시간순으로 정렬**해 한 덩어리로 제시한다.
- 각 메시지에 **발신자·채널·절대 시각**을 붙인다. `3시간 전` 같은 상대 시각은 쓰지 않는다 — 며칠 밀린 상황에서 상대 시각은 오독을 부른다.
- 묶음 머리에 **"먼저 전체를 읽고 현재 상태를 보고한다. 개별 메시지에 즉답하지 않는다"**를 넣는다. 답장은 종합 보고 다음이다.

**이것은 프롬프트 권고가 아니라 어댑터의 구조적 강제다.** LLM 의 선의에 맡기면 첫 건에 반사적으로 답하는 실패가 반복된다. 시각 정보는 이미 있다 — 봉투의 `timestamp` 와 릴레이가 붙이는 `receivedAt`(§10.6 · §10.7).

### 6.2 스레드는 두지 않는다 — 참조는 본문 안에서

슬랙·Jira·GitHub 이슈처럼 부모 메시지에 댓글을 다는 구조를 두지 않는다.

**릴레이에 상태를 요구하기 때문이다.** 그 방식은 부모가 서버에 남아 있고 자식이 그것을 참조하는데, 우리 릴레이는 드레인하면 지운다 — 부모가 사라진 뒤 자식이 올 수 있고 참조가 깨진다. 제대로 하려면 릴레이가 메시지를 보관해야 하고, 그건 무상태(§10.7)를 정면으로 깬다.

**대신 본문 안에 `replyTo` 를 둔다.** 봉투에 이미 `messageId` 가 있으므로(§10.6), 암호화된 본문에 `replyTo: <messageId>` 를 실으면 릴레이는 아무것도 모른 채 수신 측이 로컬에서 엮는다. 릴레이에 주는 메타데이터가 늘지 않으므로 §10.12 표면도 그대로다. 선택 필드이며, 없으면 단일 시간순 흐름이다.

효용 측면에서도 스레드는 사람이 **여러 갈래를 병렬로 훑기 위한 UI 장치**다. LLM 은 전체를 한 번에 읽고 종합하는 것이 자연스러워, §6.1 의 종합 보고가 대부분의 효용을 이미 가져간다. 한 채널에 갈래가 실제로 많아지면 그때 재검토한다.

### 6.3 로컬 저장소는 코어가 소유한다

릴레이는 7일 뒤 지우고 애초에 읽지도 못한다(§10.7). 대화가 남으려면 **복호화한 쪽이 남겨야 한다.**

**저장은 코어의 일이다.** "받은 것을 기록한다"에 에이전트 고유한 것이 없고, Claude 로 받았든 Codex 로 받았든 같은 기록이 남아야 §4 의 "보안 속성이 에이전트에 따라 달라지지 않는다"가 유지된다. 어댑터에 두면 두 벌로 갈리고, 그러면 어느 쪽도 전체를 보지 못한다.

저장소는 세 곳의 합류점이다 — 릴레이 드레인(§4 `both`), `inbox` 툴의 읽기 대상, 그리고 조망 UI 의 유일한 입력이다.

**이것은 평문이 디스크에 영구히 남는다는 뜻이다.** 위협 모델이 릴레이와 정반대다. 설정 파일을 `0600` 으로 막아 놓고(§11) 대화 전문을 그 옆에 평문으로 쌓으면 그 방어가 의미를 잃는다. 따라서 보관·삭제는 편의 기능이 아니라 요구사항이다.

- 저장 파일 권한은 `0600`. 설정 파일과 같은 기준이고, 넓으면 읽지 않고 죽는다.
- **보관 기한을 설정할 수 있다.** 기본값을 무제한으로 두지 않는다.
- **채널 단위 삭제(purge)** 가 있다. 채널을 떠나는 것과 그 기록을 지우는 것은 별개의 동작이다.
- 삭제는 실제 삭제다. 표시만 지우고 파일에 남기지 않는다.

**저장소를 여는 프로세스는 하나가 아니다.** 어댑터·훅·조망 UI 가 각자의 프로세스로 같은 파일을 연다. 그래서 저장소의 동시성 보장은 한 프로세스 안의 약속이 아니라 **파일에 걸린 것**이어야 한다.

- **쓰기는 파일 잠금 안에서 한다.** 읽고-고쳐-쓰는 사이에 남이 끼어들면 그 사이의 변경이 통째로 사라진다(lost update). 잠금을 들고 죽은 프로세스가 저장소를 영구히 잠그지 않도록, 오래된 잠금은 회수한다.
- **전달은 조회가 아니라 선점이다.** "미전달을 읽어 내보내고 나중에 전달됨으로 찍는다"는 두 단계 사이가 창이고, 그 사이에 다른 프로세스가 같은 것을 집으면 **같은 말이 두 번 간다**. 읽기와 표시를 한 번의 잠금 안에서 함께 하고(가시성 타임아웃), 선점한 쪽이 죽으면 기한 뒤 자동으로 풀린다.
- **표시는 내보낸 뒤에 찍는다.** 먼저 찍고 죽으면 그 메시지는 아무 데도 닿지 못한 채 사라지고, 나중에 찍고 죽으면 한 번 더 뜰 뿐이다. **중복은 보이고 유실은 안 보인다.**

### 6.4 대화는 세 축으로 갈린다

한 흐름으로 섞으면 사고가 난다. 내가 에이전트에게 한 지시가 채널로 새는 것이 가장 위험한 형태이고, 반대로 채널에서 온 말이 내 지시처럼 보이면 §7 발화 제어를 우회하는 경로가 된다.

| 축 | 상대 | 릴레이 경유 | E2E | §7 홉 제한 |
|---|---|---|---|---|
| **외부 채널** | 남과 남의 에이전트 | 지남 | 적용 | 적용 |
| **내부 위임** | 내 다른 세션 | 지남 | 적용 | 적용 안 함 |
| **나 ↔ 창구** | 내 앞의 에이전트 | 안 지남 | 해당 없음 | 무관 |

**분리는 UI 이전에 저장 시점의 일이다.** 저장할 때 축이 갈려 있어야 UI 가 무엇을 보든 섞이지 않고, 나가는 메시지는 **보내기 전에 그것이 채널로 나간다는 사실**을 보여줄 수 있다.

앞의 두 축은 **같은 메커니즘**이다 — 둘 다 채널이고, 다른 것은 참여자가 남이냐 나냐뿐이다. 내부 위임은 별도 전송로가 아니라 **참여자가 전부 내 세션인 채널**이다.

그래서 내부 위임은 **참여자마다 설정 파일이 하나씩** 있어야 성립한다. 시드가 곧 신원이므로(§9), 한 기계의 두 에이전트가 같은 설정을 읽으면 같은 키·같은 저장소를 쓴다 — 자기 자신에게 말을 거는 셈이라 채널이 서지 않는다. 그 상태에서 나는 고장은 유실이 아니라 **오배달**이다: 도착한 메시지는 §6.6 의 리스를 먼저 집는 쪽으로 가므로, 한쪽에게 온 말이 다른 쪽 세션에 뜨고 원래 수신자에게는 영영 나타나지 않으면서 **어느 화면에도 오류가 보이지 않는다.**

설치기는 에이전트별 설정을 받고(`--claude-config` / `--codex-config`), 그 값을 훅 명령에 `--config` 로 실어 못 박는다. 환경변수로 하지 않는 이유는 둘이다 — 훅 명령의 실행 방식이 에이전트마다 갈려 `VAR=x cmd` 접두가 통한다는 보장이 없고, 에이전트가 물려주는 환경에 남은 `ACM_CONFIG` 가 설치기가 정한 신원을 뒤집으면 안 된다. 그래서 우선순위는 `--config` → `ACM_CONFIG` → 기본값이다. 설정 **경로**는 토큰과 달리 비밀이 아니라 명령줄에 남아도 된다.

**기본값은 "따로"가 아니다.** 신원을 쪼개는 것은 채널 구성이 달라지는 일이라 설치기가 사용자 모르게 정할 문제가 아니다. 두 에이전트에 같은 경로를 준 경우는 의도가 아니라 실수이므로 설치기가 거부한다.

### 6.5 창구 세션과 작업 세션을 나눈다

채널과 소통하는 세션이 실제 작업까지 하면 한 컨텍스트에 세 가지가 섞인다 — 외부 대화, 나와의 대화, 그리고 코드베이스(파일·diff·테스트 출력). 마지막이 압도적으로 크다.

그러면 **대화가 코드에 밀려 압축돼 사라진다.** 며칠 밀린 메시지를 §6.1 로 종합 보고하려는데 그 세션은 이미 리팩터링으로 컨텍스트가 두 번 압축된 뒤다 — 보고할 것이 남아 있지 않다. 역방향도 있다. 작업 세션이 채널을 직접 보면 작업 중 나온 모든 판단이 채널로 나갈 후보가 되어 **§7 이 무력해진다.**

그래서 분리는 성능 최적화가 아니라 **경계 유지**다. 창구 세션은 대화와 결정을 들고, 작업 세션은 코드를 든다. 창구가 결정을 지시로 바꿔 넘기고, 작업 세션이 결과를 돌려준다. 지시가 여러 갈래면 작업 세션도 여럿이다.

**위임은 내부 채널로 한다 — 에이전트 내장 세션 메시징을 쓰지 않는다.** Claude Code 에는 세션 간 메시징이 있으나 아래 넷이 전부 어긋난다.

| | 내장 세션 메시징 | 내부 채널 |
|---|---|---|
| 받는 쪽이 꺼져 있으면 | 전달 실패, **발신 측에 알림 없음** | 큐에 남았다가 뜰 때 받는다 |
| 다른 머신으로 | 단방향 — 회신 주소가 없다 | 양방향 |
| 기록 | 남지 않는다 | 로컬 저장소에 남는다(§6.3) |
| 대상 | 같은 OS 유저 안에서도 일부만 | 키를 가진 누구든, 에이전트 무관 |

대상 제약은 OS 유저에서 끝나지 않는다. 같은 머신·같은 OS 유저의 세션이 **서로 목록에 나타나지조차 않는 경우가 실측된다.** 무엇이 그 경계를 정하는지는 문서화돼 있지 않고, 우리가 통제하는 변수도 아니다 — 에이전트 구현이 바꾸면 따라 바뀐다. 위임 대상이 **관측 불가능한 규칙으로 정해진다는 것 자체**가 문제다. 내부 채널은 키로 정해지므로 그 규칙에 의존하지 않는다.

**기록이 결정적이다.** 내장 메시징은 위임한 사실 자체가 어디에도 남지 않아, 병렬로 굴리면 "무엇을 지시했고 무엇이 아직 안 돌아왔는지"를 아무도 모른다. 유실이 조용하다는 점과 겹치면 위임하고 잊는 순간 사라진다. 대상 범위도 다르다 — 내부 채널로 하면 **Claude 와 Codex 사이의 위임**이 그대로 성립한다.

**즉시성을 대가로 내주지 않는다.** 병렬 세션을 굴린다는 것은 내가 그 세션들 앞에 없다는 뜻이다. 폴링만으로는 "지시했는데 세 시간째 아무도 안 봤다"가 실제로 나므로, 도착을 세션에 알리는 것은 §6.6 이 별도로 책임진다 — 훅은 두 에이전트 모두에 있고, 작업 중인 세션에도 턴 도중에 닿는다.

**내부 채널도 교환 절차는 외부와 같다.** 프로젝트마다 채널이 갈리므로(A 프로젝트 세션이 B 프로젝트 위임을 볼 이유가 없다 — §6 와 같은 논리), 내부라고 신원·채널 비밀 교환을 생략하지 않는다. 지름길을 한 번 열면 "내 세션이니 검증 없이 붙여도 된다"는 판단이 코드에 남고, 그 전제가 깨지는 순간(다른 머신·공유 머신·나중에 남을 초대) 조용히 뚫린다.

세션마다 신원을 갈라 두는 것에는 이득이 따라온다 — **누가 보냈는지가 서명으로 확인된다.** 병렬 세션에서 위임 기록의 발신자가 자기 신고가 아니게 된다.

절차를 지키는 것과 손으로 하는 것은 다르다. 같은 머신·같은 유저 안에서 어댑터가 프로젝트 단위로 신원과 채널을 준비하는 것은 **자동화이지 생략이 아니다** — 교환은 그대로 일어나고 신뢰 경계를 넘지 않는다. 외부 채널의 수동 교환(§5.2)은 그대로다.

### 6.6 도착을 세션이 알게 하는 세 경로

**MCP 툴은 모델이 부를 때만 실행되고, 모델은 턴이 있어야 움직인다.** 표준 MCP 에는 서버가 세션에 말을 거는 경로가 없다 — 프로토콜에 `notifications/*` 가 있지만 그것이 모델의 대화 흐름에 들어가지는 않는다. `claude/channel` 이 특별한 지점이 정확히 여기다(§4).

그래서 어댑터가 백그라운드로 릴레이를 폴링해 저장소를 최신으로 유지하는 것과, **세션이 그것을 아는 것**은 다른 문제다. 경로가 셋이고 즉시성이 다르다.

| 경로 | 언제 알게 되나 | 조건 |
|---|---|---|
| **채널 주입** | 즉시. 세션이 유휴여도 | Claude + 개발 채널 플래그 |
| **훅** | 턴이 도는 중이면 다음 툴 호출 직후, 유휴면 다음 프롬프트 | Claude · Codex 둘 다 |
| **툴 응답 편승** | 모델이 우리 툴을 부를 때 | 어디서나 |

셋을 전부 구현하고, **가능한 것을 전부 켠다.** 하나만 고르면 그것이 막힐 때 통째로 막힌다 — 주입은 개발 플래그에 걸려 있고, 훅은 에이전트가 그 이벤트를 노출해야 한다.

**훅은 두 에이전트 모두에 있고 형식이 같다.** `hooks.json` 구조와 이벤트 이름(`SessionStart`·`UserPromptSubmit`·`PostToolUse`·`Stop`·`PreCompact` 등)이 호환되며, 둘 다 `hookSpecificOutput.additionalContext` 로 **모델 컨텍스트에 실제로 들어간다**(사용자에게만 보이는 `systemMessage` 와 다르다). 그래서 훅 스크립트는 에이전트별로 갈리지 않는다 — §4 의 어댑터 경계가 여기서도 유지된다.

**훅은 동기로만 등록한다.** Codex 는 async 훅을 지원하지 않고, 만나면 등록 목록에서 **통째로 뺀 뒤** 경고 한 줄만 남긴다(`hooks/list` 의 `warnings`). 파일에는 남아 있는데 한 번도 돌지 않으므로 눈으로는 정상으로 보인다 — 정확히 이 문서가 막으려는 "동작하는 것처럼 보이는 고장"이다. 턴 도중 도달은 async 가 아니라 **`PostToolUse`** 가 맡는다. 툴 호출마다 도는 동기 훅이라 긴 작업을 도는 세션도 턴 경계를 기다리지 않는다.

**Codex 훅의 조정값은 camelCase 로 쓴다.** `timeout` 과 `additionalContextLimit` 이 읽히는 이름이다. 문서와 바이너리에 `timeout_sec`·`additional_context_limit` 이라는 이름도 보이지만 설정 파일 파서는 그것을 읽지 않는다 — 조용히 버리고 기본값(600초·무제한)으로 떨어져, 아래 "훅이 싣는 양은 우리가 정한다"가 통째로 무효가 된다.

**훅 파일은 `codex doctor` 가 검사하지 않는다.** 일부러 깨뜨린 JSON 도 `config.load: ok` 로 통과한다. 실제로 무엇이 등록됐는지 확인하는 유일한 길은 `codex app-server` 에 JSON-RPC `hooks/list` 를 던져 `warnings`·`errors` 와 등록된 항목을 직접 보는 것이다.

**MCP 프로토콜만으로는 어느 에이전트에서도 안 된다.** 서버가 보내는 `notifications/*` 는 Codex 에서 전부 로그로 흘러가고 모델에 닿지 않으며, Claude 도 `claude/channel` 확장이 아니면 같다. 그래서 **어댑터와 훅은 별개 프로세스**이고 로컬 저장소가 둘을 잇는다 — 어댑터가 릴레이에서 받아 저장하고, 훅이 그것을 읽어 주입한다.

**훅은 설치 대상이다.** Codex 훅은 trust 승인을 요구하고 스크립트가 바뀌면 해시가 달라져 재승인이 필요하다. 설치 절차가 훅 등록과 그 승인 안내까지 포함하지 않으면, 사용자는 "MCP 는 붙었는데 알림만 안 오는" 상태에 빠진다 — §4 가 전달 방식을 명시로만 정하는 것과 같은 이유로, 이 상태를 조용히 허용하지 않는다.

**섞이지 않게 하는 것은 지시문이 아니라 상태다.** 저장소의 각 메시지에 **전달 여부**를 둔다. 주입이 나가면 표시하고, 훅은 미전달분만 본다. 이렇게 하면 주입이 도는 세션에서 훅은 조용하고, 주입이 실패했거나 세션이 놓쳤을 때만 뜬다 — 훅은 알림이 아니라 **안전망**이다. 이 상태가 없으면 같은 메시지가 두 번 도착한 것처럼 보인다.

**주입에는 합류 시간(coalescing window)이 필요하다.** 주입은 턴 없이 꽂히므로 3건이 1분 간격으로 오면 주입이 세 번 일어나고, §6.1 의 "묶어서 한 번에"가 깨진다. 도착 즉시 쏘지 말고 짧게 모았다가 내보내며, 그 사이에 온 것은 같이 묶는다. 훅은 프롬프트 시점에 쌓인 것을 보므로 자연히 묶인다.

**훅이 싣는 양은 우리가 정한다.** 훅 출력은 모델 컨텍스트로 그대로 들어가므로 밀린 큐가 수백 건이면 그 턴을 통째로 밀어낸다. 게다가 에이전트 쪽 컨텍스트 상한(Codex `additionalContextLimit`)은 **넘친 만큼을 그냥 잘라 내며**, 잘린 자리가 문장 중간이라 모델은 그것이 원문인 줄 안다. 그래서 건수와 글자 수 양쪽에 예산을 두고 **메시지 사이에서** 끊는다. 자를 거면 몇 건이 남았는지 함께 알리고, 실은 것 외에는 선점을 곧바로 풀어 다음 훅이 이어서 집게 한다. 한 건이 예산보다 커도 그 한 건은 내보낸다 — 아니면 그 메시지에서 영원히 진행이 멈춘다.

**보고 형식을 프롬프트 룰로 주입하지 않는다.** "쌓인 것은 요약해서 먼저 보고하라" 같은 지시문은 컨텍스트가 압축되면 사라지고, 모델이 무시해도 막을 방법이 없다. 대신 §6.1 대로 **어댑터가 묶어서 내보낸다** — 2건 이상이면 개별 메시지를 볼 방법 자체가 없고, 모델에게 도달하는 형태가 이미 시간순 묶음이다.

## 7. 발화 제어

에이전트끼리 자율로 대화하면 목적 없는 무한 왕복에 빠진다. 사람 채팅에 없는 실패 양식이므로 프로토콜이 직접 막는다.

| 장치 | 내용 |
|---|---|
| **멘션 기반 발화** | 자신이 명시적으로 호출되지 않으면 읽되 응답하지 않는다 |
| **홉 제한** | 한 사슬의 연속 왕복에 상한을 둔다. 초과하면 사람에게 넘긴다 |
| **예산 상한** | 채널·작업 단위로 메시지/토큰 예산을 둔다. 소진하면 정지한다 |
| **에코 억제** | 자신이 유발한 메시지에 자동 응답하지 않는다 |

원칙은 하나다 — **종료 조건 없는 대화를 만들지 않는다.** 목적이 끝나면 채널은 조용해져야 한다.

**판정과 전달을 분리한다.** 발화 판정이 `false` 여도 메시지는 세션에 전달된다 — "읽되 응답하지 않는다"가 멘션 규칙의 정의이고, 전달까지 막으면 그건 발화 제어가 아니라 필터링이다. 세션은 판정 결과를 함께 받아 응답 여부를 정한다.

**홉 수는 본문에 실어 보낸다.** 헤더는 평문이라(§10.6) 거기 두면 릴레이가 대화 구조를 보게 된다. 본문에 두면 AEAD 로 보호되고 발신자만 정할 수 있다. 발신자가 위조할 수 있다는 점은 변하지 않으며, 그건 예산이 받친다 — 홉 제한은 사슬 길이를, 예산은 총량을 막으므로 위조로 앞의 것을 피해도 뒤의 것에 걸린다.

**예산은 툴 경로에서도 강제한다.** 모델이 발화 툴을 직접 부르는 길이 예산 우회로가 되면 총량 장치가 무의미해진다.

## 8. 접근 통제

채널마다 발신자 허용목록을 둔다. 목록에 없는 발신자의 메시지는 조용히 버린다.

권한 중계(permission relay)를 켜면 채널 상대가 내 세션의 도구 사용을 승인·거부할 수 있다. **허용목록에 넣는 것은 그 권한을 주는 것과 같다.** 문서와 CLI 양쪽에서 이 사실을 분명히 경고한다.

## 9. 지문 검증 UX

공개키 지문은 사람이 음성·대면·다른 경로로 대조할 수 있어야 한다.

**128비트를 PGP 워드 리스트 16단어로 표시한다.** 지문 = `SHA-256(SHA-256(서명 공개키))` 앞 128비트.

지문이 덮는 것은 **서명 공개키 하나**다. 사람이 음성으로 읽어 맞추는 값이라 대조 대상을 둘로 늘릴 수 없고, 발신자 진정성(§8)의 근거가 서명키이므로 그쪽을 덮는다. 따라서 **공개키 블록은 두 키를 한 덩어리로 교환한다** — sign 만 대조하고 kem 을 다른 경로로 받는 흐름을 만들지 않는다. 바꿔치기된 KEM 키는 지문 대조로 잡히지 않는다.

```
  beeswax   puberty    sawdust   crucifix
  sawdust   guitarist  drifter   determine
  ruffled   revenue    crowfoot  racketeer
  slowdown  forever    lockup    councilman

  fp: 1bba b23d b269 4e47 b0ca 42be c05f 7f3b
```

**왜 128비트인가.** 공격자는 자기 키를 마음대로 고를 수 있으므로 필요한 것은 충돌 저항이 아니라 **제2 역상(second-preimage) 저항**이다 — n비트에 2ⁿ 작업. Matrix 의 7개 이모지(42비트)를 따라하면 안 된다. 그건 상대가 추측을 먼저 확정해야 하고 시도가 1회뿐인 **대화형** SAS 라 안전한 수치다. 우리 지문은 정적·장기 식별자라 공격자가 오프라인에서 무한히 갈아 볼 수 있다.

**왜 앞자리만 보면 안 되는가.** 최적화하지 않은 단일 코어 JS 로 측정한 값:

| 맞추려는 앞자리 | 소요 |
|---|---|
| 16비트 (hex 4자) | **8.3초** |
| 24비트 (hex 6자) | 34분 |
| 32비트 (hex 8자) | 6.3일 |

GPU 최적화 코드는 이보다 몇 자릿수 빠르다. **앞 4~8자만 확인하는 사용자는 보호받지 못한다.** 따라서 UX 가 전체 대조를 자연스러운 행동으로 만들어야 하고, **잘라낸 short id 를 어디에도 노출하지 않는다** — 그건 앞자리 공격에 공식 승인을 붙이는 셈이다.

**왜 PGP 워드 리스트인가.** 1995년 Juola·Zimmermann 이 **음성 전달용으로 설계**한 목록이다 — 2음절 256개·3음절 256개가 위치에 따라 교대하고, 단어가 음소 거리로 선별돼 있다. 교대 구조 덕에 단어를 빠뜨리거나 순서를 바꾸면 검출된다. BIP39 는 **필기 백업용**(고유 4글자 접두)이라 음성에는 맞지 않는다.

## 10. 암호 설계

Bun 1.3.12 에서 실측 검증한 결과에 기반한다.

### 10.1 라이브러리

```jsonc
"@hpke/core":             "^1.9.0",
"@hpke/dhkem-x25519":     "^1.8.0",
"@hpke/chacha20poly1305": "^1.8.0",
"@noble/ciphers":         "^2.3.0",
"@noble/curves":          "^2.3.0",
"@noble/hashes":          "^2.3.0"
```

네이티브 모듈·postinstall·WASM 초기화가 없다. 사용자가 MCP 서버로 설치하는 도구라 배포 마찰이 없어야 한다.

**Bun 내장 WebCrypto 는 쓸 수 없다.** 실측:

| 연산 | 결과 |
|---|---|
| `subtle.generateKey({name:"X25519"})` | OK |
| **`subtle.deriveBits({name:"X25519"})`** | **실패 — `NotSupportedError`** |
| `subtle.generateKey({name:"ChaCha20-Poly1305"})` | 실패 |
| Ed25519 sign/verify, AES-GCM, HKDF | OK |

X25519 키를 만들 수는 있지만 **KEM 에 필요한 Diffie-Hellman 을 못 한다.** `@hpke/dhkem-x25519` 는 SubtleCrypto 를 호출하지 않고 `@noble` 을 내부에 품고 있어 동작한다 — 이 문서에서 가장 중요한 구현 세부사항이고, Bun 의 WebCrypto 변동(PR #34838 등 활발히 병합 중)에 영향받지 않는 이유다.

> 정직하게: noble 2.x 의 최신 감사는 **자체 감사**다. 독립 감사(Cure53 2024, Trail of Bits 2023, Kudelski 2023)는 0.x/1.x 대상이다. 문서에 "독립 감사됨"이라고 쓰지 않는다.

**구현 시 걸리는 API 함정** (실제로 걸려서 기록):

- `@hpke/core` v1.x 는 **인스턴스**를 요구한다 — `new HkdfSha256()`. `KdfId` enum 을 넘기면 `InvalidParamError`.
- `serializePublicKey`/`serializePrivateKey` 는 **`ArrayBuffer`** 를 반환한다. noble 함수는 `Uint8Array` 만 받으므로 `new Uint8Array(buf)` 로 감싼다. 안 하면 `TypeError: expected Uint8Array, got type=object`.
- noble 2.x 는 import 에 **명시적 `.js` 확장자**가 필요하다 — `@noble/curves/ed25519.js`.

### 10.2 알고리즘

| 용도 | 선택 |
|---|---|
| 신원 | **Ed25519**(서명) + **X25519**(KEM), 32B 시드 하나에서 `deriveKeyPair` 로 파생 |
| 키 래핑 | **HPKE Base 모드** — DHKEM(X25519, HKDF-SHA256) / HKDF-SHA256 / ChaCha20-Poly1305 |
| 본문 | **XChaCha20-Poly1305** — 메시지마다 랜덤 256비트 콘텐츠 키 + 랜덤 192비트 nonce |
| 발신자 인증 | 봉투에 대한 **분리된 Ed25519 서명** (HPKE Auth 모드 아님) |
| 지문 | SHA-256(SHA-256(서명 공개키)) 앞 128비트 → PGP 워드 16단어 (§9) |
| key id | SHA-256("agent-channel-mesh/v1/keyid" ‖ KEM 공개키 ‖ 서명 공개키) 앞 64비트 (§10.12) |
| 재전송 방지 | seq·timestamp·채널 태그를 **AAD 에 결속** + 발신자별 1024비트 슬라이딩 윈도우 |

**왜 HPKE 인가.** X25519+HKDF+AEAD 를 직접 조합하면 도메인 분리와 컨텍스트 결속에서 미묘하게 틀리기 쉽다. RFC 9180 은 그 결속을 명세하고 테스트 벡터를 제공한다.

**왜 Auth 모드가 아닌가.** HPKE Auth 는 발신자를 **한 수신자에게만** 인증한다. N명 채널에서는 수신자마다 별도 auth 컨텍스트가 필요하고, 멤버끼리 "다른 사람이 본 발신자가 나와 같은가"를 확인할 수 없다. Base 모드 + 분리 서명이면 모든 멤버가 같은 발신자 결속을 검증한다.

**왜 XChaCha20 인가 — 구조적 이유.** 랜덤 96비트 nonce 는 한 키 아래 2³² 메시지쯤에서 생일 한계에 닿아 카운터를 쓰게 만든다. 그런데 **브릿지는 에이전트가 죽였다 살리는 서브프로세스**라 카운터를 잃으면 nonce 를 재사용하고, 그건 치명적이다. XChaCha20 의 **192비트** nonce 는 영구히 랜덤 생성해도 충돌 확률이 무시할 수준이다. 메시지마다 새 콘텐츠 키를 쓰면 재시작 상태 문제가 아예 사라진다.

### 10.3 N명 채널 — 수신자별 팬아웃

그룹 키를 두지 않는다. 본문은 한 번 암호화하고, 콘텐츠 키를 수신자 수만큼 HPKE 로 감싼다.

실측 (500B 메시지, 구현된 `seal()` 기준 — 상세는 §10.6):

```
팬아웃 N=20     15.72 ms/건   오버헤드 1928 B
1:1 직접         1.97 ms/건   오버헤드  256 B
개봉             1.58 ms/건   (N 무관 — 자기 몫만 언랩)
```

**16ms·1.9KB.** LLM 추론 지연(초 단위) 옆에서 무의미한 비용이다. 대신 얻는 것이 크다 — **회전할 그룹 키가 없다.** 멤버 추가·제거는 다음 메시지의 수신자 목록이 달라지는 것뿐이다.

**MLS(RFC 9420)는 구조적으로 불가능하다.** §14 원문:

> "Applications **MUST** have an established way to resolve conflicting Commit messages for the same epoch."

MLS 는 같은 epoch 의 충돌하는 Commit 을 애플리케이션이 직렬화하도록 **의무화**한다. 상태 없는 릴레이에는 직렬화 권위가 없으므로 커밋 순서에 대한 분산 합의를 우리가 만들어야 한다. 생태계 성숙도 문제가 아니라 전제조건을 충족할 수 없는 문제다.

**sender-keys 도 맞지 않는다.** O(N) 설정 후 O(1) 이라 Signal 규모에서는 훌륭하지만, **멤버 제거 시 모든 발신자가 자기 sender key 를 회전·재배포**해야 한다. 3~20명에 멤버 변동이 잦은 환경에서 20ms 를 아끼려고 그 복잡도를 사는 셈이다.

**유출되는 것**: 래핑된 키 개수 = 그룹 크기, 수신자별 key id = 멤버 구성. 이는 §10.7 이 이미 밝히는 메타데이터 노출의 일부이고, 그 이상의 완화(회전 key id, 수신자 목록 패딩)는 릴레이가 라우팅을 못 하게 만들거나 봉투를 부풀린다 — 메타데이터 보호를 목표로 하는 설계라면 mixnet 층이 필요하고, 그것은 이 프로젝트가 아니다(§10.9).

### 10.4 순방향 비밀성 — 없다. 그대로 밝힌다

RFC 9180 §9.1 원문:

> "HPKE ciphertexts are not forward secret with respect to recipient compromise in any mode."

즉 **발신자 측 FS 는 있고, 수신자 측 FS 는 없다.** 공격자가 브릿지의 장기 개인키를 훔치고 릴레이 트래픽을 녹음해 뒀다면 전체 이력을 복호화한다.

래칫을 넣지 않는 이유:

1. **래칫은 1:1 이다.** N명이면 N² 세션(20명 = 190쌍). 그룹 문제를 풀지 못한다 — Signal 도 그 위에 sender-keys 를 얹는다.
2. **X3DH 는 prekey 서버가 필요하다.** 일회용 prekey 를 보관하고 정확히 한 번 소비·삭제하는 상태 — 우리 릴레이가 갖지 않기로 한 바로 그 상태다.
3. **프로세스 재시작을 견디는 상태 저장이 필요하다.** "래칫 전진"과 "저장" 사이에 죽으면 세션이 깨진다. 실제 클라이언트의 "복호화 불가" 버그 대부분이 여기서 나온다.
4. **스킵된 키 DoS.** 순서 뒤바뀜에 대비해 스킵 키를 저장해야 하고, 무제한 저장은 문서화된 DoS 벡터다.

그리고 현실적 위협 모델을 보면 — 개인키는 개발자 노트북에 있고, 공격자가 거기서 코드를 실행할 수 있으면 **평문도 이미 갖는다**(에이전트 컨텍스트, 로컬 저장소, 래칫 상태). 래칫이 주로 막는 것은 지속적 접근 없는 키 탈취(백업·디스크 이미지)인데, **그 경로는 로컬 저장소가 이미 더 넓게 열어 둔다** — 녹음된 트래픽을 푸는 것보다 §6.3 의 평문 사본을 읽는 편이 쉽다. 즉 여기서 래칫을 넣어도 실질 위협은 줄지 않고, 실제로 줄이는 것은 §10.14 의 보관 기한과 삭제다.

**Double Ratchet 을 직접 구현하지 않는다.** 실패가 조용하다 — 미묘하게 틀린 래칫도 테스트는 통과하면서 약속한 FS 를 전혀 제공하지 않는다. 도입한다면 `@signalapp/libsignal-client`(Bun 에서 네이티브 바인딩 실행 확인됨)를 쓴다.

### 10.5 재전송 방지 — 브릿지가 한다

릴레이는 신뢰 대상이 아니다. 재전송할 수 있는 공격자가 릴레이 자신인 경우가 많으므로 **릴레이 측 재전송 방지는 보안 연극**이다. 브릿지가 신뢰 경계이고 로컬 디스크를 가지므로 브릿지가 강제한다.

1. `(채널 태그, 발신자 key id, seq, timestamp)` 를 **AEAD 의 AAD 에 결속**한다. AAD 변조가 거부되는 것은 실측 확인 — seq 를 고치면 복호화가 깨진다. 권고가 아니라 암호학적 결속이다.
2. **슬라이딩 윈도우** (IPsec/DTLS 방식, RFC 4303·6479) — 발신자별 high-water-mark + 최근 seq 1024비트 비트맵. 윈도우 아래는 거부, 이미 켜진 비트는 거부, 나머지는 수용 후 시프트.
3. **신선도 윈도우** (±5분) 로 dedup 캐시를 유한하게 유지. 시계 오차가 실패 양식이 되므로 걸릴 때 명확히 로깅한다.
4. **검사 순서는 싼 것부터** — 구조 → 발신자 조회 → **서명** → 신선도 → seq 윈도우 → dedup → *그다음* 비싼 비대칭 언랩. 재전송 폭주가 X25519 연산을 소모하지 않게 한다.

**서명이 재전송 검사보다 앞선다.** 순서를 뒤집으면 재전송 방지 자체가 DoS 수단이 된다 — 공격자가 서명 없는 위조 봉투로 seq 를 선점해 그 자리의 정상 메시지를 영구히 막을 수 있다. 서명을 먼저 통과한 봉투만 상태를 갱신하므로, 실패한 봉투는 어떤 흔적도 남기지 않는다.

**순서는 호출자 재량이 아니다.** `receive()` 한 곳에 고정한다 — `open()` 과 guard 를 따로 부르면 순서를 틀려도 모든 검사가 통과하고 4항이 약속한 성질만 조용히 사라진다.

**dedup 은 발신자가 부여한 message id** 로 하고 AAD 결속으로 검증한다. 내용 주소 id(암호문 해시)는 우아해 보이지만 악의적 릴레이가 프레이밍을 바꿔 같은 메시지에 다른 id 를 만들 수 있다.

**순서**는 발신자별 seq(재전송 방지용으로 이미 필요)로 발신자별 순서와 누락을 잡고, 표시 순서는 timestamp 정렬 + 발신자 key id 로 tie-break 한다. 벡터 클록은 여기서 과설계다 — 20명이면 메시지마다 20개 카운터를 싣는데, 그 대가로 얻는 것은 사람이 읽는 대화에서 구분되지 않는 인과 순서다.

### 10.6 평문 봉투

| 필드 | 크기 | 평문인 이유 | 유출 |
|---|---|---|---|
| magic | 4 B | 형식 판별 | — |
| 채널 태그 | 16 B | 라우팅 | 채널 연결 |
| 메시지 id | 16 B | dedup | — |
| 발신자 key id | 8 B | 키 선택 | **소셜 그래프** |
| 시퀀스 번호 | 8 B | 재전송·순서 | 메시지 양 |
| timestamp | 8 B | 신선도 | **활동 패턴** |
| nonce | 24 B | AEAD | — |
| 수신자 수 | 4 B | 파싱 | **그룹 크기** |
| key id + 래핑된 키 | (8 + 80) B × N | 수신자별 언랩 | **그룹 크기·구성** |
| 본문 암호문 + 태그 | len + 16 B | — | **메시지 길이** |
| 발신자 서명 | 64 B | 진정성 | — |

**두 자리의 key id 는 §10.12 와 같은 값이다** — `SHA-256("agent-channel-mesh/v1/keyid" ‖ KEM 공개키 ‖ 서명 공개키)` 앞 8바이트(§10.2). 발신자 자리의 것은 수신자가 서명 검증용 공개키를 고르는 데 쓰고, 수신자 목록의 것은 각자 자기 몫의 래핑된 키를 찾는 데 쓴다. 릴레이에게는 큐 인덱스이며, 폴링 인증이 대조하는 대상도 이 값이다.

**래핑된 키 80B 의 내역**: HPKE `enc`(X25519 임시 공개키) 32B + 봉인된 콘텐츠 키 32B + Poly1305 태그 16B. 세 항 중 콘텐츠 키 본체를 빠뜨리면 56B 가 나오는데, 그 값은 실측과 맞지 않는다.

실측 (본문 500B, `encode()` 출력 기준):

| N | 봉인 | 전송 크기 | 오버헤드 |
|---|---|---|---|
| 1 | 1.97 ms | 756 B | 256 B |
| 2 | 2.40 ms | 844 B | 344 B |
| 20 | 15.72 ms | 2428 B | 1928 B |

개봉은 1.58 ms(N 무관 — 자기 몫 하나만 언랩한다). 메시지가 커질수록 오버헤드 비율은 급격히 좋아진다.

**회전 채널 태그**(`HMAC(채널 비밀, epoch)`)로 릴레이는 고정 채널 id 대신 회전하는 불투명 태그만 본다(§10.11). 본문은 크기 버킷으로 패딩해 길이에서 내용을 추정하지 못하게 한다.

**범위 밖**: PIR, mixnet, Pond 계열. 이 프로젝트 목표를 훨씬 넘는 지연과 인프라를 요구하며, 그것을 감당하는 순간 "코딩 에이전트가 쓰는 메시징"이 아니게 된다.

### 10.7 릴레이는 "logic-stateless" 다

오프라인 전달에는 저장이 필요하므로 릴레이에 TTL 붙은 blob 저장소(Vercel KV·Upstash Redis)가 있어야 한다. 그걸 단서 없이 "stateless" 라 부르면 오해를 부른다. README 표현은 이렇게 한다:

> 릴레이는 **논리적으로 무상태**다 — 장기 프로세스를 돌리지 않고 세션·래칫·그룹 상태를 갖지 않는다. 오프라인 전달을 위해 암호화된 blob 을 TTL 저장소에 보관하며, 그 내용은 읽을 수 없다.

### 10.8 README 에 정직하게 쓸 네 가지

1. **수신자 키 유출에 대한 순방향 비밀성이 없다.** 장기 키 탈취 + 트래픽 녹음 = 전체 이력 복호화.
2. **메타데이터는 노출된다.** 릴레이는 소셜 그래프·시각·크기·그룹 크기를 보고, 폴링하는 쪽의 서명 공개키까지 받으므로 그 지문도 계산할 수 있다(§10.12).
3. **릴레이는 논리적 무상태이나 암호화 blob 을 저장한다.**
4. **로컬에는 평문이 남는다.** 릴레이가 못 읽는 것과 내 디스크에 없는 것은 다르다(§6.3 · §10.14).

### 10.9 채택하지 않는 것

미룬 목록이 아니라 **기각 목록**이다. 각각 전제가 우리 구조와 충돌하거나, 사는 복잡도가 얻는 것을 넘는다.

| 항목 | 기각 근거 |
|---|---|
| Double Ratchet / PCS | prekey 서버 상태 + 원자적 영속화 + N² 세션. 게다가 로컬 평문 사본이 있는 한(§6.3) 실질 위협이 줄지 않는다 — 도입한다면 `libsignal-client`, **직접 구현 금지** |
| MLS / RFC 9420 | RFC 9420 §14 가 Commit 직렬화를 **의무화**하는데 상태 없는 릴레이에 직렬화 권위가 없다. 성숙도가 아니라 전제조건 문제다 |
| sender-keys | 멤버 제거가 발신자별 O(N) 회전을 부른다. 3~20명 규모에서 20ms 를 아끼려고 살 복잡도가 아니다 |
| 벡터 클록 / HLC | 메시지마다 N개 카운터를 실어 얻는 인과 순서가, 사람이 읽는 대화에서 timestamp 정렬과 구분되지 않는다 |
| sealed sender, PIR, mixnet | 메타데이터 보호를 목표로 삼으면 지연·인프라가 다른 제품이 된다(§10.6) |
| 양자 내성 (ML-KEM 하이브리드) | HPKE PQ 하이브리드 ciphersuite 가 표준화 중이다. 확정 전에 자체 조합하는 것은 §10.1 의 금지선이다 |

### 10.10 남은 불확실성

- 벤치마크는 M 계열 머신 **단발 측정**이다. 방향은 맞지만 엄밀하지 않다.
- Bun 의 WebCrypto 는 변동 중이다. 위 실패는 1.3.12 기준이며 개선될 것으로 보인다 — 권고는 어느 쪽이든 의존하지 않도록 짰다.

**해소됨** — PGP 워드 리스트는 Zimmermann 의 원문 PDF 에서 파싱해 vendoring 했고, 정본 벡터 두 개(`E58294F2…` 20단어, `82E5` → `miser travesty`)로 검증한다. 256/256, 중복·교집합 없음.

### 10.11 채널 태그와 채널 비밀

채널은 **32바이트 공유 비밀**을 갖고, 봉투의 채널 태그는 거기서 파생한다.

```
채널 태그 = HMAC-SHA256(채널 비밀, "agent-channel-mesh/v1/channel-tag" ‖ epoch)[0..16]
```

epoch 는 0 에서 시작한다 — 회전 전까지 태그는 채널당 상수다. **회전은 epoch 를 올리는 것뿐**이며, 그때 봉투 형식도 멤버십도 바뀌지 않는다.

**채널 id 를 그대로 태그로 쓰지 않는 이유**: 태그는 릴레이에 평문으로 보이므로, 그것이 곧 채널 id 면 회전할 방법이 없다. 파생을 처음부터 끼워 두면 회전이 값 하나 바꾸는 일이 된다. 지금 직결해 두면 나중에 봉투 형식을 고쳐야 한다.

**채널 비밀은 멤버만 안다.** 초대는 이 비밀을 상대에게 전달하는 것이고, 그 전달은 이미 있는 1:1 암호 경로(§10.2)를 탄다 — 릴레이는 비밀을 보지 못한다.

**비밀을 아는 것과 멤버인 것은 다르다.** 비밀은 태그를 계산해 *어느 채널인지* 알 뿐이고, 메시지를 읽으려면 자기 KEM 키로 래핑된 콘텐츠 키가 있어야 한다(§10.3). 나간 멤버가 비밀을 기억해도 이후 메시지의 수신자 목록에서 빠지므로 읽지 못한다. **비밀 회전은 멤버 제거의 필수 조건이 아니다** — 그래서 §10.3 의 "회전할 그룹 키가 없다"가 유지된다.

### 10.12 수신함 폴링은 서명으로 인증한다

큐를 여는 유일한 열쇠가 key id 라면 **key id 만 알면 누구나 남의 큐를 비울 수 있다.** 내용이 읽히지는 않지만(콘텐츠 키는 수신자의 X25519 개인키로만 풀린다) 정상 수신자가 그 메시지를 못 받는다 — 가용성 공격이다. key id 는 봉투 평문 헤더에 있으므로(§10.6) 트래픽을 보는 쪽은 이미 알고 있다.

재전송으로 완화하려는 접근은 답이 아니다. 발신자 재전송과 dedup(§10.5)이 있어 영구 손실 대신 지연이 되지만, **비우는 쪽이 계속 비우면 지연이 무한하다.** 완화책을 방어로 부르지 않는다.

**서명된 폴링으로 막되, 릴레이에 상태를 만들지 않는다.** 릴레이가 key id → 공개키 매핑을 저장하고 검증하는 방식이면 그 등록·회전·폐기가 전부 상태가 되어 §10.7 과 충돌한다. 대신 **요청이 두 공개키와 서명을 함께 싣는다.**

```
GET /fetch/<key id>
  X-ACM-Kem:   <KEM 공개키, hex 64자>
  X-ACM-Sign:  <Ed25519 서명 공개키, hex 64자>
  X-ACM-Sig:   Ed25519(서명키, "acm/v1/fetch" ‖ key id ‖ timestamp ‖ nonce), hex 128자
  X-ACM-Time:  <unix ms, 10진수>
  X-ACM-Nonce: <16바이트, hex 32자>
```

**헤더가 다섯인 이유는 무상태 검증의 정의 그대로다** — 검증에 필요한 것이 전부 요청 안에 있어야 한다. 릴레이는 서명 대상 바이트를 스스로 재구성해야 서명을 볼 수 있으므로 그 재료인 `timestamp` 와 `nonce` 가 실려야 하고, 서명을 검증할 공개키와 key id 소유를 확인할 공개키가 각각 필요하므로 두 공개키가 실려야 한다. 하나라도 빠지면 릴레이는 저장된 상태로 그것을 메워야 하고, 그 순간 §10.7 과 충돌한다.

**서명 대상의 레이아웃은 고정 44바이트다.**

```
"acm/v1/fetch"(12 B) ‖ key id(8 B) ‖ timestamp(8 B, big-endian uint64) ‖ nonce(16 B)
```

**길이 접두를 넣지 않는다.** 네 필드가 전부 고정 길이라 이어붙이기에 모호성이 없다 — 서로 다른 `(key id, timestamp, nonce)` 조합이 같은 44바이트로 접힐 수 없으므로, 길이 접두가 막아 줄 혼동 자체가 존재하지 않는다. 대신 **조립 함수가 입력 길이를 강제한다**. 고정 길이라는 가정이 깨지는 순간 이 논증도 같이 깨지므로, 가정을 문서가 아니라 코드가 지킨다.

**key id 는 두 공개키를 함께 묶어 파생한다.**

```
key id = SHA-256("agent-channel-mesh/v1/keyid" ‖ KEM 공개키 ‖ 서명 공개키)[0..8]
```

한쪽 공개키만으로 뽑으면 소유 검사가 아무것도 보장하지 않는다. 서명은 Ed25519 키로 하는데 key id 가 X25519 키에서만 나온다면, 그 둘은 같은 시드에서 **서로 다른 HKDF 라벨로 갈라져 한쪽에서 다른 쪽을 계산할 수 없고**(§10.2), KEM 공개키는 **채널 멤버 전원이 이미 들고 있다**(§10.3 의 수신자 목록). 그래서 공격자는 피해자의 KEM 공개키에 자기가 방금 만든 서명 키쌍을 붙여 제시하면 된다 — key id 도 맞고 서명도 자기 키로 검증되므로 남의 큐를 그대로 드레인한다. 두 키를 함께 해시하면 **제시된 서명키가 큐 주인의 것임이 key id 자체로 증명된다.** 릴레이는 여전히 매핑을 저장하지 않는다 — 계산으로만 확인한다.

**이 공격의 주체는 채널 동료다.** 순수 망 관측자는 봉투 평문 헤더에서 key id 8바이트만 보므로(§10.6) KEM 공개키를 역산해야 하고, 그건 2⁶⁴ 벽이다. 막지 못했던 것은 KEM 공개키를 정당하게 아는 쪽 — 같은 채널의 멤버다. 위협 주체를 "공격자"로 뭉뚱그리면 이 구분이 사라지고, 그러면 왜 8바이트 key id 로 충분해 보였는지도 설명되지 않는다.

릴레이가 하는 검증은 셋이다. 순서는 비용이 아니라 의미로 정한다 — 뒤 단계가 앞 단계의 결론에 의존한다.

1. `timestamp` 가 허용 창(구현 기본값 5분) 안인지. 창은 양방향으로 본다 — 클라이언트 시계가 앞서는 것도 스큐이지 공격이 아니다.
2. `key id == keyIdOf(KEM 공개키, 서명 공개키)` — 이 요청이 그 큐의 주인 것인지.
3. 서명이 유효한지. 2번을 통과했으면 서명키가 큐 주인의 것임은 확정됐으므로, 서명 검증이 곧 "주인이 이 요청을 만들었다" 가 된다. 2번 없이 서명만 보면 "누구의 서명인지" 를 모르는 채 검증하는 셈이라 아무 의미가 없다.

**재전송 경계는 시간 창이고, nonce 는 재전송을 막지 않는다.** 릴레이는 무상태라(§10.7) 이미 본 nonce 를 기억할 수 없다 — 그래서 창 안에 캡처된 요청은 그대로 재생된다. nonce 의 역할은 **서명 유일성 확보**다: 같은 밀리초에 두 번 서명해도 서명 바이트가 겹치지 않는다. 캡처 자체는 TLS 가 막지만 그것은 전송 계층의 보장이고 이 인증이 주는 성질이 아니다. 두 층을 합쳐 "재전송을 막는다"고 쓰지 않는다.

**서명 대상은 위 네 요소뿐이다 — 요청 URL 을 서명하지 않는다.** 경로와 쿼리스트링은 **배포 인프라가 바꿀 수 있는 값**이다. 라우팅 계층은 경로를 재작성하고 경로 조각을 쿼리 파라미터로 옮기며, 프록시·게이트웨이는 파라미터를 덧붙이거나 순서를 바꾼다. 서명 대상에 URL 이 들어가면 클라이언트는 변형 전 문자열을, 릴레이는 변형 후 문자열을 서명하므로 불일치가 100% 로 굳는다.

이 고장은 **로컬 테스트에서 재현되지 않는다.** 로컬에는 그 변형을 가하는 계층이 없기 때문이다. 배포해야만 나타나고, 그때는 "서명 검증이 항상 실패하는" 형태로 나타나 원인이 암호 쪽에 있는 것처럼 보인다. 그래서 서명 대상을 고정된 네 요소로 못박는다 — 인증되는 것은 우리가 바이트로 만들어 넣은 값뿐이고, 전송 경로가 손댈 수 있는 표현은 넣지 않는다.

**릴레이는 여전히 아무것도 기억하지 않는다.** 검증에 필요한 것이 전부 요청 안에 있고, 검증이 끝나면 남기는 것이 없다. 즉 무상태와 인증이 양자택일이 아니었다.

**대신 릴레이가 아는 것이 늘어난다.** 이 인증은 서명 공개키를 릴레이에 넘기므로, 릴레이는 §9 지문(`SHA-256(SHA-256(서명 공개키))` 앞 128비트)을 계산할 수 있다 — key id 8바이트만 보던 때에는 못 하던 일이다. 서명 기반 폴링 인증의 고유 비용이고 어떤 설계로도 피할 수 없다: 서명을 검증하려면 검증키가 있어야 한다. 늘어난 것은 **식별자의 정밀도**뿐이며 메시지 내용에는 여전히 닿지 못한다. 그래도 §10.8 의 "메타데이터는 노출된다" 항목이 한 칸 더 나빠진 것이므로 숨기지 않는다.

**드레인은 이 검증을 통과한 요청만 한다.** 검증 실패는 빈 큐가 아니라 오류다 — 조용히 빈 응답을 주면 공격과 정상 상태를 구분할 수 없다.

### 10.13 봉투 올리기는 배포 토큰으로 인증한다

**막는 피해는 기밀이 아니라 가용성이다.** 아무나 올릴 수 있으면, 남의 key id 로 쓰레기 봉투를 큐 상한만큼 밀어 넣는 것만으로 **아직 못 받은 진짜 메시지를 큐 밖으로 밀어낼 수 있다** — 큐는 상한에서 가장 오래된 것부터 버리기 때문이다. 올린 쪽은 200 을 받고 당한 쪽은 아무것도 못 받는다. 이 프로젝트가 가장 피하려는 형태의 고장, 조용한 유실이다.

**§10.12 와 물음이 다르다.** 폴링은 "이 수신함이 네 것이냐"를 묻고, 답이 요청 안에서 스스로 완결된다 — 두 공개키로 key id 를 다시 계산하면 끝이다. 쓰기에는 그런 물음이 없다. 채널 멤버십은 종단 간 사실이라 브릿지의 신뢰 목록에만 있고(§8), 릴레이에는 조회할 테이블이 없다(§5.1 · §10.7). 릴레이가 답할 수 있는 물음은 하나뿐이다 — **"이 릴레이를 쓸 자격이 있느냐."**

**봉투 서명으로 대신하지 않는다.** 공격자는 키쌍을 얼마든지 새로 만들 수 있으므로 "서명돼 있다"는 아무것도 거르지 못한다. 그러면서 발신자의 서명 공개키를 릴레이에 넘겨 §10.8 의 메타데이터 노출만 넓힌다 — 얻는 것 없이 잃기만 한다.

```
POST /post
  Authorization: Bearer <배포 토큰>
```

**토큰은 채널 접근 제어가 아니다.** 토큰을 가진 쪽은 여전히 아무 채널에나 올릴 수 있다 — 그것을 막는 것은 수신자의 검증(§8)이지 이 토큰이 아니다. 이 토큰이 정하는 것은 "누가 이 릴레이에 봉투를 얹을 수 있는가" 하나뿐이며, 그 이상을 주장하지 않는다.

**비교는 내용에도 길이에도 시간이 의존하지 않게 한다.** 양쪽을 먼저 해시한 뒤 XOR 로 누적한다. §10.12 와 반대인 것이 의도다 — 거기서 견주는 값은 전부 공개라 시간이 새어도 잃을 것이 없지만, 여기서 견주는 것은 비밀 그 자체다.

**기본값을 두지 않는다.** 쓰기 정책은 릴레이를 세우는 모든 자리에서 **명시해야 넘어가는 인자**다(`--delivery` 와 같은 원칙). 기본값을 두면 그 기본값이 곧 배포의 보안이 되고, 세운 쪽은 자기가 무엇을 고른 적 없다는 사실조차 모른다. 여는 것도 고르는 것이므로 열려면 열겠다고 적는다.

**토큰 없이 공개 주소에 뜨지 않는다.** 루프백 밖이거나 서버리스면 기동에서 죽는다 — 조용히 열린 채로 뜨는 것보다 낫다. **우회 플래그를 만들지 않는다.** 그런 플래그는 복사되어 기본값이 되고, 그 순간 이 검사는 없는 것과 같아진다. 공개로 열려면 토큰을 만든다(`openssl rand -hex 32`).

**토큰은 환경변수로만 받는다.** 플래그로 주면 `ps` 에 그대로 찍혀 같은 기계의 다른 사용자가 프로세스 목록만으로 가져간다.

**검사는 본문을 읽기 전에 끝낸다.** 인증을 뒤에 두면 그 앞 단계 — 최대 1MB 짜리 본문을 메모리로 끌어오는 일 — 가 통째로 공격자에게 무료로 열린다.

### 10.14 로컬 평문 보관 — 릴레이와 반대 방향의 위협

§10 의 나머지는 전부 **전송 중**을 다룬다. 로컬 저장소(§6.3)는 그 반대다 — 복호화된 평문이 디스크에 남는다.

여기서 릴레이 쪽 성질이 하나도 도움이 되지 않는다. 릴레이는 읽지 못하고 7일 뒤 지우지만, 로컬 사본은 읽히고 지워지지 않는다. **위협 주체가 다르다** — 릴레이 운영자·망 관측자가 아니라, 그 기계에 접근하는 쪽이다.

| 대상 | 보호 |
|---|---|
| 같은 기계의 다른 OS 유저 | 파일 권한 `0600` (설정 파일과 같은 기준, §11) |
| 백업·동기화로 새어 나가는 사본 | 보관 기한 — 오래된 것은 남지 않는다 |
| 기계를 넘기거나 잃을 때 | 채널 단위 purge — 실제 삭제 |

**설정 파일만 지키는 것으로는 부족하다.** `config.json` 을 `0600` 으로 막는 근거는 "이 파일 하나로 모든 암호가 무력화된다"인데, 대화 전문이 옆에 평문으로 쌓이면 공격자는 키를 풀 필요조차 없다.

**저장하지 않는 선택지는 없다.** 릴레이가 7일 뒤 지우고 드레인하면 사라지므로(§5.3), 남기지 않으면 §6.1 의 종합 보고도 §6.4 의 조망도 성립하지 않는다. 그래서 방향은 "안 남긴다"가 아니라 **"남기되 기한과 삭제를 사용자가 통제한다"** 다.

## 11. 설정 — 어댑터가 무엇으로 서는가

어댑터는 에이전트가 띄우는 stdio 서브프로세스다. 대화창이 없으므로 시드도 채널 비밀도 물어볼 수 없다. **파일이 유일한 입력이다.**

시드를 매번 새로 만들지 않는 이유는 §9 다 — 프로세스가 재시작될 때마다 신원이 바뀌면 대역 외로 대조한 지문이 즉시 무효가 되고, 지문 검증이라는 장치 자체가 성립하지 않는다. 그래서 32바이트 시드 하나를 저장하고 나머지는 전부 재파생한다(§10.2).

```json
{
  "seed": "<32바이트 hex>",
  "relay": "https://relay.example",
  "relayToken": "<그 릴레이가 요구하는 쓰기 토큰, §10.13>",
  "channels": [
    {
      "secret": "<32바이트 hex>",
      "name": "팀",
      "members": [{ "label": "bob", "sign": "<hex>", "kem": "<hex>" }],
      "mentions": ["alice"]
    }
  ]
}
```

**권한을 검사해서 막는다.** 이 파일에는 개인키(시드)와 채널 비밀이 들어간다 — 그 둘이면 과거·미래 메시지를 전부 읽을 수 있다. 그룹이나 타인에게 한 비트라도 열려 있으면 **읽지 않고 죽는다**. 문서로만 경고하면 지켜지지 않고, 지켜지지 않은 상태가 조용히 정상 동작한다. 그 뒤의 모든 암호는 이 파일 하나로 무력화되므로, 여기서 실패하는 편이 낫다.

**잘못된 설정은 즉시 죽는다.** 길이가 어긋난 키를 잘라서 쓰거나 모르는 인자를 기본값으로 흘리지 않는다 — 반쪽으로 동작하는 메시징은 고장을 성공처럼 보이게 한다.

### 11.1 배포 형태 — 레포 하나가 두 에이전트의 마켓플레이스다

**참여자는 레포를 클론하지 않는다.** 클론해서 경로를 손으로 등록하는 절차는 세 군데(MCP 등록·훅 등록·설정 경로)를 사람이 맞춰야 하고, 하나만 어긋나도 §6.6 의 "붙었는데 알림만 안 오는" 상태가 된다. 플러그인은 그 셋을 한 번에 못 박는다.

**두 에이전트가 같은 목록을 읽는다.** Codex 가 아는 매니페스트 경로는 `.claude-plugin/marketplace.json` · `.claude-plugin/plugin.json` · `.codex-plugin/plugin.json` 셋이다. 즉 마켓플레이스 파일은 Claude 것을 **그대로 공유**하고, 플러그인 매니페스트만 자기 것을 먼저 본다. 그래서 레포 하나 · 목록 하나 · 훅 파일 하나에 매니페스트만 둘이면 양쪽이 같은 등급으로 선다 — §4 의 코어/어댑터 경계가 배포 형태에서도 유지된다.

```
.claude-plugin/marketplace.json     ← Claude·Codex 가 같이 읽는다
plugin/
  .claude-plugin/plugin.json        ← delivery: both
  .codex-plugin/plugin.json         ← delivery: inbox
  hooks/hooks.json                  ← 둘이 같이 읽는다
```

**플러그인 루트를 레포 루트로 두지 않는다.** 레포 루트를 그대로 쓰면 개발용 `CLAUDE.md` 가 플러그인 컨텍스트로 딸려 들어가 검증에 걸린다. 껍데기 디렉토리를 따로 두면 배포되는 것이 매니페스트와 훅뿐임이 파일 구조로 드러난다.

**플러그인은 소스가 아니라 함께 커밋된 번들을 돌린다.** 플러그인은 클론만 되고 의존성 설치는 일어나지 않으므로, `${CLAUDE_PLUGIN_ROOT}` 의 소스를 부르면 첫 실행에서 모듈을 못 찾고 죽는다. 설치 단계 없이 도는 길은 **의존성이 들어 있는 단일 파일**(`plugin/dist/acm.js`)이고, 그것을 레포에 함께 커밋한다. 레지스트리를 거치지 않으므로 팀원이 돌리는 코드는 그 커밋과 정확히 같다 — 배포 시점의 레지스트리 상태가 훅 동작을 가르지 못한다.

**번들이 소스와 어긋나는 것은 바이트로 막는다.** `Bun.build` 산출은 결정적이라, 지금 소스에서 다시 뽑은 결과와 커밋된 파일이 같은지를 테스트가 대조한다. 이 검사가 없으면 소스만 고치고 다시 뽑지 않은 상태 — **고친 적 없는 코드가 배포되는 상태** — 가 레포를 읽어서는 드러나지 않는다.

**MCP 실행 형태는 에이전트마다 다르다.** 변수 확장이 갈리기 때문이다: 훅의 `command` 는 양쪽 다 `${CLAUDE_PLUGIN_ROOT}` 를 치환하지만, MCP 서버의 `args` 는 Claude 만 치환한다. Codex 는 치환하지 않는 대신 자식 프로세스의 `cwd` 를 플러그인 루트 기준으로 푼다. 그래서 Claude 는 `args` 에 절대 경로를, Codex 는 `cwd: "."` + 상대 경로를 쓴다. 반대로 적으면 **오류 없이 서버가 뜨지 않는다** — 매니페스트를 생성기 한 곳이 소유하는 이유다.

**설정이 없는 첫 실행에는 말을 하는 서버가 뜬다.** 플러그인이 깔리는 자리는 에이전트·마켓플레이스·버전에 따라 갈리는 캐시 경로라, 사람에게 "이 명령을 쳐라" 라고 줄 수 있는 경로가 없다. 설정 파일이 없다고 어댑터가 죽으면 깐 사람에게는 **툴이 통째로 없는 것**으로만 보이고, 훅도 같은 이유로 조용히 지나간다. 그래서 설정이 없을 때는 `setup` 툴 하나만 가진 별도 서버가 뜬다(§11). 코어를 무르게 만들지 않으려고 서버 자체를 분리한다 — `serve` 는 여전히 온전한 노드를 요구한다.

**매니페스트는 손으로 쓰지 않는다.** 훅 목록이 설치기와 갈리면 "설치 경로마다 동작이 다른" 고장이 난다 — 이벤트를 하나 추가했을 때 스크립트로 깐 사람에게만 알림이 오고 플러그인으로 깐 사람에게는 안 온다. 이벤트 정의는 한 곳에 두고 매니페스트는 거기서 생성하며, 커밋된 파일이 생성 결과와 같은지는 테스트가 지킨다.

**설치 직후는 `untrusted` 다.** Codex 는 플러그인 훅에 승인을 요구하고 버전이 바뀌면 다시 요구한다(§6.6). 설치 안내가 그 승인까지 포함하지 않으면 사용자는 알림이 없는 상태를 정상으로 받아들인다.

## 12. 데스크탑 앱 — 에이전트 대화를 보는 창

터미널만으로는 §6.4 의 세 축이 보이지 않는다. 창구 세션 하나와 작업 세션 여럿이 병렬로 돌면, 어디에 무엇이 오갔는지를 사람이 터미널을 옮겨 다니며 눈으로 훑는 수밖에 없다. 지시가 어디로 갔고 무엇이 아직 안 돌아왔는지는 그렇게 봐서는 알 수 없다.

### 12.1 정체성 — 부속 UI 가 아니다

앱이 보여주는 것은 **내 에이전트들이 어디서 무슨 대화를 하고 있는가**이고, 외부 채널은 그중 한 종류다. 채널을 하나도 쓰지 않고 병렬 세션만 굴리는 사용자에게도 §6.4 의 내부 위임 축은 그대로 필요하다.

그래서 앱은 별도 레포다. Rust 툴체인·앱 서명·릴리스 주기가 플러그인과 전부 다르고, 플러그인 레포에 웹 소스를 얹으면 그 셋이 한 레포의 CI 에 묶인다.

**다만 독립 제품이지 독립 기능은 아니다.** 앱이 보여줄 기록은 플러그인이 만든다 — 저장소 형식은 코어가 소유하고(§6.3), 앱은 그 소비자다. 형식이 바뀌면 앱이 따라간다.

### 12.2 앱은 뷰어가 아니라 세션을 띄운다

세션 간 대화를 수동으로 긁어 보여주는 방식은 성립하지 않는다. Claude Code 의 내장 세션 메시징은 같은 머신이면 로컬 소켓이라 기록을 남기지 않고, 다른 머신·클라우드면 Anthropic 서버에만 남아 접근할 수 없다. **기록이 있으려면 우리 경로를 지나야 한다**(§6.5).

그리고 §6.6 의 즉시성 문제가 여기서 풀린다. 유휴 작업 세션은 사용자가 프롬프트를 칠 때까지 위임이 온 줄 모르는데, 사용자가 각 터미널 앞에 있을 수 없다. 앱이 ACP(Agent Client Protocol)로 세션을 기동하면 **앱이 그 세션을 소유하므로**, 저장소에 미전달분이 있을 때 앱이 세션을 깨울 수 있다.

- 에이전트는 앱이 띄우는 로컬 프로세스다 — 브라우저 탭은 프로세스를 띄우지 못하므로 순수 웹으로는 성립하지 않는다. 이것이 데스크탑 앱인 이유다.
- 구독 플랜 인증을 그대로 쓴다. 앱이 별도 자격을 요구하지 않는다.
- 그 세션이 우리 MCP 어댑터를 로드하므로, **코어·어댑터에 앱 전용 코드가 없다.** 앱은 §4 의 경계 밖에 선다.

### 12.3 터미널 작업은 대체하지 않는다

앱이 세션을 띄울 수 있다고 해서 작업까지 앱 안으로 끌고 오지 않는다. 목적은 채팅이 아니라 **작업**이고, 코드를 만지는 것은 터미널의 그 세션이다. 채널은 그 작업에 대해 의견을 나누고 겹치지 않게 하는 수단이다.

```
              ┌─ 터미널 세션          ← 실제 작업
플러그인 ──────┤
 (MCP 어댑터)  └─ 데스크탑 앱 (ACP)   ← 조망·보고·유휴 세션 기동

      둘 다 같은 코어 · 같은 로컬 저장소를 본다
```

**합류점은 로컬 저장소다.** 터미널에서 받은 것과 앱에서 받은 것이 같은 곳에 쌓이고 양쪽이 같은 것을 본다. 이것이 없으면 같은 대화가 두 벌로 갈린다.

### 12.4 앱이 지켜야 하는 것

앱은 평문을 다루는 유일한 GUI 다. §6.3·§10.14 의 요구가 여기서 사용자에게 보이는 형태가 된다.

- **세 축을 섞어 보여주지 않는다.** 축은 저장 시점에 이미 갈려 있고(§6.4), 앱은 그것을 유지한다.
- **나가는 메시지는 보내기 전에 어디로 나가는지 보인다.** 외부 채널로 나가는 것과 내 세션에 보내는 것이 같은 입력창을 공유하면 안 된다.
- **지문은 자르지 않는다**(§9). 화면이 좁다는 것은 이유가 되지 않는다.
- **보관 기한과 채널 단위 삭제를 사용자가 조작할 수 있다**(§6.3). 이 조작면이 없으면 그 요구는 설정 파일 주석으로만 존재하게 된다.
- **채널 비밀을 화면에 띄우지 않는다.** 그것을 가진 쪽은 그 채널에 쓸 수 있다(§5.2).
