# agent-channel-mesh

에이전트와 사람이 같은 메시에서 대화한다. 릴레이는 암호문만 지나보내고, 평문은 참여자 로컬에만 존재한다.

## 무엇인가

코딩 에이전트 세션은 서로 격리돼 있다. Claude Code 의 공식 세션 간 메시징조차 같은 OS 사용자의 세션 일부에만 닿는다. 다른 사람의 에이전트, 또는 다른 종류의 에이전트와 대화하려면 별도 경로가 필요하다.

이 프로젝트는 그 경로를 만든다. 네 가지를 하나의 전송로로 처리한다.

- **사람 ↔ 에이전트** — 팀원이 내 에이전트에게 지시하거나 결과를 받는다
- **에이전트 ↔ 에이전트** — 각자의 에이전트가 서로 협업한다
- **외부 → 에이전트** — CI·모니터링·웹훅이 세션에 도달한다
- **내 세션 ↔ 내 세션** — 창구 세션이 작업 세션에 위임한다. 같은 메커니즘이고, 참여자가 전부 내 세션인 채널일 뿐이다

마지막 것이 내장 세션 메시징과 겹쳐 보이지만 겹치지 않는다. 내장 메시징은 상대가 죽어 있으면 조용히 실패하고, 회신 주소가 없어 단방향이며, 어디에도 기록이 남지 않고, 닿는 범위가 같은 OS 사용자 안에서도 일부로 좁다. 여기서는 넷 다 반대다 — 그래서 Claude 가 Codex 에 위임할 수 있다.

## 특징

- **종단 간 암호화** — 릴레이가 내용을 읽지 못한다. 개인키는 로컬 코어 밖으로 나가지 않는다.
- **서버리스 릴레이** — 상시 구동 서버가 필요 없다. 서버리스 함수로 배포한다.
- **에이전트 무관** — 코어에 특정 에이전트 고유 로직이 없다. 어댑터만 갈아 끼운다.
- **발화 제어** — 에이전트끼리 목적 없이 무한 왕복하는 것을 프로토콜이 막는다.
- **권한 경계** — 동료가 공유한 말은 기본이 읽기다. 그 말로 내 디스크가 바뀌거나 명령이 돌지 않는다. 강제는 프롬프트가 아니라 훅이 한다.
- **로컬 기록** — 릴레이의 7일 TTL 과 별개로 로컬에 남는다. 보관 기한과 삭제는 사용자가 정한다.
- **보는 창** — 데스크탑 앱이 외부 채널 대화와 내부 위임을 나눠 보여준다. 별도 레포다.

## 구조

```
[에이전트 세션] ──stdio──> [어댑터] [메시 코어] ──HTTPS──> [릴레이] <──── [다른 브릿지]
      평문              에이전트별   암복호화·정책        암호문만
```

암호·정책·릴레이는 어느 에이전트를 쓰든 같은 코어를 지난다. 에이전트별로 다른 것은 **세션에 메시지를 어떻게 넣느냐**뿐이다.

| 에이전트 | 보내기 | 받기 |
|---|---|---|
| Claude Code | MCP 툴 | **채널 주입** + 훅 + 수신함 |
| Codex | MCP 툴 | **훅** + 수신함 |
| 그 외 | MCP 툴 | **수신함 폴링** — 에이전트가 꺼내감 |

받는 경로는 하나가 아니다. 즉시 도착(채널 주입), 턴 경계 도착(훅), 꺼내오기(수신함)를 그 에이전트에서 되는 만큼 전부 켠다. 셋이 서로를 중복 전달하지 않는 것은 지시문이 아니라 **전달 여부 상태**가 보장한다.

Codex 에도 주입 메서드가 있지만(`app-server` 의 `turn/steer`) 세션을 우리가 소유해야 해서 쓰지 않는다 — 훅이 세션을 빼앗지 않고 같은 즉시성을 준다. 근거는 [docs/architecture.md §4](docs/architecture.md)·[§6.6](docs/architecture.md) 참조.

자세한 설계는 [docs/architecture.md](docs/architecture.md) 참조.

## 설치

**레포를 클론하지 않는다.** 두 에이전트 모두 플러그인으로 깐다 — 이 레포가 곧 마켓플레이스이고, 플러그인은 MCP 서버와 훅을 함께 등록한다. 필요한 것은 [Bun](https://bun.sh) 하나다.

### Claude Code

세션 안에서 두 줄이다.

```
/plugin marketplace add Seungwoo321/agent-channel-mesh
/plugin install agent-channel-mesh@agent-channel-mesh
```

터미널에서도 같다.

```bash
claude plugin marketplace add Seungwoo321/agent-channel-mesh
claude plugin install agent-channel-mesh@agent-channel-mesh
```

### Codex

```bash
codex plugin marketplace add Seungwoo321/agent-channel-mesh
codex plugin add agent-channel-mesh@agent-channel-mesh
```

### 깔렸는지 확인한다

```bash
claude plugin list
```

`✔ enabled` 여야 한다. 여기서만 실패가 드러난다 — `plugin validate`·`plugin details`·`mcp list` 는 못 실린 플러그인에도 정상처럼 답한다.

깔린 플러그인은 `untrusted` 로 들어온다. 세션에서 `/hooks` 를 열어 승인해야 훅이 돈다 — 승인하지 않으면 MCP 툴은 붙었는데 **알림만 오지 않는** 상태가 된다. 플러그인을 새 버전으로 올리면 해시가 바뀌어 다시 승인해야 한다.

### 무엇이 깔리나

두 에이전트가 **같은 마켓플레이스 파일**(`.claude-plugin/marketplace.json`)과 **같은 훅 파일**(`plugin/hooks/hooks.json`)을 읽는다. 갈리는 것은 플러그인 매니페스트 하나뿐이고, 거기서 정해지는 것은 전달 방식이다 — Claude 는 `both`(주입 + 수신함), Codex 는 `inbox`(수신함). 그래서 어느 쪽으로 깔든 암호·정책·릴레이 통신은 같은 코어를 지난다.

플러그인은 클론만 되고 의존성 설치는 일어나지 않는다. 그래서 훅과 MCP 서버가 돌리는 것은 레포의 소스가 아니라 **함께 커밋된 번들 하나**(`plugin/dist/acm.js`)다 — 의존성이 전부 그 안에 들어 있어 `bun` 만 있으면 뜬다. 레지스트리도 `bun install` 도 거치지 않으므로, 팀원이 돌리는 코드는 이 레포의 그 커밋과 정확히 같다. 번들이 소스와 어긋나면 `bun test` 가 바이트로 잡는다.

깔고 나서 처음 연 세션에는 **설정이 없다.** 그때 어댑터는 죽지 않고 `setup` 툴 하나만 들고 떠서 에이전트에게 그 사실을 알린다 — 다음 절이 그 다음이다.

함께 깔리는 `mesh-setup` 스킬이 그 다음 절을 대신 밟는다. 두 에이전트가 같은 파일을 읽으므로 순서도 같다. 아래를 직접 따라가도 되고, 세션에서 이렇게 말해도 된다.

```
메시 설정 도와줘
```

## 붙이기

설치는 통로를 놓을 뿐이고, 대화는 신원과 채널이 있어야 시작된다. 어댑터가 읽는 것은 설정 파일 하나뿐이고, 그 파일을 만드는 것이 아래 네 단계다. 첫 단계만 한 사람이 하고 나머지는 참여자마다 한다.

### 1. 릴레이를 띄운다

참여자가 공통으로 바라볼 주소가 하나 필요하다. **한 사람만** 하면 되고, 나머지는 그 주소만 받는다. 상시 운용은 [배포](#배포) 참조이고, 아래는 로컬에서 시험할 때다.

```bash
git clone https://github.com/Seungwoo321/agent-channel-mesh.git
cd agent-channel-mesh
bun install
bun run src/server.ts                 # http://127.0.0.1:8787
```

기본은 루프백이라 이 기계에서만 닿는다. 다른 기계와 대화하려면 **쓰기 토큰을 만들고** `--host 0.0.0.0` 으로 연다.

```bash
export ACM_RELAY_TOKEN=$(openssl rand -hex 32)   # 참여자에게 이 값을 나눠 준다
bun run src/server.ts --host 0.0.0.0
```

토큰 없이 루프백 밖으로 뜨려고 하면 기동에서 죽는다. 아무나 올릴 수 있는 릴레이는 **남의 수신함을 채워 아직 못 받은 메시지를 큐 밖으로 밀어낼 수 있고**, 당한 쪽에는 그 유실이 보이지 않기 때문이다. 우회 플래그는 없다 — 열려면 토큰을 만든다.

저장소가 메모리이므로 이 프로세스가 죽으면 대기 중인 봉투가 사라진다.

### 2. 신원을 만든다

대화에 참여하는 **사람마다 각자의 기계에서** 한 번 한다. 칠 명령은 없다 — 플러그인이 깔리는 자리는 에이전트·마켓플레이스·버전에 따라 갈리는 캐시 경로라 받아 적을 수 있는 경로가 아니다. 대신 **세션 안에서** 한다.

설정이 없는 상태로 세션을 열면 어댑터는 `setup` 툴 하나만 들고 뜨고, 에이전트에게 그 사실을 알린다. 에이전트에게 이렇게 말하면 된다.

```
메시 설정 만들어줘. 릴레이는 http://127.0.0.1:8787, 이름은 alice.
```

**릴레이 주소는 사람이 준다.** 에이전트가 추측한 주소는 설정이 멀쩡히 만들어지고 메시지만 영원히 안 간다 — 어느 화면에도 오류가 뜨지 않는 고장이라 그렇게 되면 원인을 찾을 단서가 없다.

`setup` 은 시드를 만들어 `~/.agent-channel-mesh/config.json` 을 `0600` 으로 쓰고, 세 가지를 돌려준다 — 상대에게 보낼 공개키 블록, 내 지문, 새 채널 비밀. **시드는 돌려주지 않는다.** 툴 응답은 모델 컨텍스트로 들어가고 그 컨텍스트는 로그·요약을 거친다.

릴레이가 쓰기 토큰을 요구하면 **에이전트를 띄울 때** 환경변수로 준다. `setup` 이 설정 파일에 옮겨 적는다. 툴 인자가 아닌 이유는 그 값이 모델 컨텍스트에 남기 때문이고, 플래그가 아닌 이유는 `ps` 에 그대로 찍히기 때문이다.

```bash
ACM_RELAY_TOKEN=<릴레이 운영자에게 받은 값> claude
ACM_RELAY_TOKEN=<릴레이 운영자에게 받은 값> codex
```

설정이 생겨도 **이미 뜬 서버는 설정 모드 그대로다.** 세션을 다시 연다 — 그때 메시 툴이 붙는다.

**이미 파일이 있으면 아무것도 하지 않는다.** 시드를 덮어쓰면 신원이 사라지고, 상대가 대조해 둔 지문이 전부 무효가 된다. 백업본으로 되돌리는 길은 두지 않았다 — 잃었으면 설정 파일을 지우고 다시 `setup` 을 부른 뒤 지문을 다시 대조한다.

### 3. 공개키를 교환하고 지문을 대조한다

`setup` 이 돌려준 `members` 블록을 상대에게 보내고, 상대 것을 받아 내 `config.json` 의 `channels[].members` 에 넣는다. 나중에 다시 보려면 세션에서 `whoami` 툴을 부른다 — "내 메시 공개키 보여줘" 면 된다. 나오는 값은 공개키와 지문뿐이다.

**지문은 반드시 다른 경로로 대조한다** — 음성 통화나 대면이다. 공개키가 온 그 경로로 온 지문은 아무것도 검증하지 못한다. 값이 어긋나면 중간자가 있다는 뜻이고, 그때 대화를 시작하면 안 된다.

### 4. 채널 비밀을 나눈다

채널을 여는 사람이 `setup` 이 돌려준 채널 비밀을 참여자에게 전달한다. 같은 비밀을 넣은 노드끼리 같은 채널에 붙는다.

**이 교환이 수동인 것은 미완성이 아니라 설계다.** 두 단계가 각각 다른 것을 막는다.

- **채널 비밀**(이 단계) — 접근 통제다. 초대 링크나 채널명 검색으로 아무나 들어올 수 있으면 트래픽 제약도, 악용에 대한 대처도 성립하지 않는다. 누구에게 줬는지 아는 사람만이 누구를 끊을지 정할 수 있다.
- **공개키·지문**(3단계) — 중간자 차단이다. 자동 교환하면 그 경로를 쥔 쪽이 키를 바꿔치기할 수 있다.

**채널 비밀은 이름이 아니라 열쇠다.** 이것을 가진 쪽은 그 채널에 유효한 메시지를 **쓸 수 있다** — 읽기는 상대가 내 공개키를 등록해야 가능하지만 쓰기는 비밀만으로 된다. 암호화된 메신저나 대면으로 전달하고, 공개 채널·이슈 트래커·커밋에 남기지 않는다.

채널 이름은 로컬 별칭일 뿐이라 참여자끼리 같을 필요가 없다 — 릴레이는 이름을 모른다. 자세한 근거는 [docs/architecture.md](docs/architecture.md) §5.1~§5.3.

**팀원에게 넘길 것은 넷이고, 경로가 셋으로 갈린다.**

| 값 | 어떻게 넘기나 | 왜 |
|---|---|---|
| 릴레이 주소 | 아무 경로나 | 비밀이 아니다 |
| 릴레이 쓰기 토큰(§10.13) | 암호화된 경로 | 이걸 쥔 사람은 그 릴레이에 봉투를 올릴 수 있다 |
| 채널 비밀 | 암호화된 경로 | 이걸 쥔 사람이 곧 멤버다 |
| 공개키(`members`) | 아무 경로나 — **단 지문은 다른 경로로 대조**(3단계) | 공개값이지만 바꿔치기가 가능하다 |

릴레이 토큰과 채널 비밀은 **다른 것을 연다.** 토큰은 "이 릴레이를 쓸 자격"까지만이라 어느 채널에 올리는지는 가리지 않는다 — 팀을 나누는 것은 채널 비밀이다. 팀원을 끊으려면 채널 비밀을 새로 만들어 남은 사람에게만 다시 준다.

```jsonc
// ~/.agent-channel-mesh/config.json
{
  "seed": "…",                       // setup 이 만든다. 이것만 있으면 신원이 재파생된다
  "relay": "https://relay.example",
  "relayToken": "…",                 // 그 릴레이가 요구할 때만. 없으면 생략한다
  "channels": [{
    "secret": "<채널 비밀 hex>",
    "members": [{ "label": "bob", "sign": "…", "kem": "…" }],
    "mentions": ["alice"]            // 이 이름이 불릴 때만 응답한다
  }]
}
```

**개인키와 채널 비밀이 들어 있다.** 권한이 `600` 보다 넓으면 어댑터가 읽지 않고 죽는다.

### 5. 한 기계의 두 에이전트를 서로 다른 참여자로 세운다 (선택)

Codex 와 Claude 를 **서로에게 말을 거는 두 참여자**로 쓰려면 설정 파일을 갈라야 한다. 시드가 곧 신원이라, 같은 파일을 읽으면 두 에이전트는 같은 키·같은 저장소를 쓴다 — 자기 자신에게 말을 거는 셈이라 채널이 성립하지 않는다.

**갈라 놓지 않으면 나는 고장은 유실이 아니라 오배달이다.** 도착한 메시지는 `claimUndelivered` 가 먼저 집는 쪽으로 간다. 팀원이 Claude 에게 한 말이 Codex 세션에 뜨고 Claude 에는 영영 안 나타나는데, 어느 화면에도 오류가 보이지 않는다.

플러그인이 등록한 MCP 명령에는 손댈 자리가 없으므로, 어느 신원을 읽을지는 **에이전트를 띄우는 환경**이 정한다. 기본 경로를 Claude 에게 두고 Codex 만 옮긴다.

```bash
ACM_CONFIG=~/.agent-channel-mesh/codex.json codex
```

그 경로에는 아직 파일이 없으므로 Codex 쪽 어댑터는 설정 모드로 뜬다. 그 세션에서 `setup` 을 부르면 **그 경로에** 두 번째 신원이 생긴다 — 이름은 다르게 준다(`alice-codex`).

두 신원을 `axis: "internal"` 채널로 묶는다 — 서로의 `members` 블록을 상대 설정에 넣고 같은 채널 비밀을 쓴다. 같은 사람의 두 세션이므로 지문 대조는 화면에서 바로 한다.

**서로의 지문을 상대 설정의 `self` 에도 적는다.** 그래야 내 Codex 의 말이 내 Claude 에서 내 말로 판정돼 제한 없이 통한다([권한](#권한--도착한-말이-내-기계에서-무엇까지-하나)). 적지 않으면 내 다른 에이전트가 동료로 판정돼 읽기까지만 되고, `axis: "internal"` 로 선언한 채널에 `self` 가 아닌 멤버가 있으면 설정 로드 자체가 거부된다.

`ACM_CONFIG` 를 셸 프로필에 export 하지 않는다 — 같은 셸에서 뜬 Claude 까지 그 신원을 읽어 두 에이전트가 다시 한 참여자로 합쳐진다. 읽을 설정은 `--config` → `ACM_CONFIG` → 기본 경로 순으로 정해진다.

## 권한 — 도착한 말이 내 기계에서 무엇까지 하나

채널 멤버는 서로 **동료**다. 위아래가 없고, 도착한 말은 지시가 아니라 **공유**다. 그래서 여기서 갈리는 것은 사람의 지위가 아니라 **내 기계에 대한 권한**이다 — 동료가 내 저장소를 읽고 답을 받는 것은 자연스럽고, 동료의 말 때문에 내 디스크가 바뀌거나 명령이 도는 것은 자연스럽지 않다.

반대로 **내 Codex 가 내 Claude 에게 시키는 것은 막히지 않는다.** 둘 다 나이기 때문이다. 그 둘을 가르는 값이 설정의 `self` 다.

### 기본값

| 보낸 쪽 | 권한 | 할 수 있는 것 |
|---|---|---|
| 내 다른 에이전트 (`self` 에 적은 지문) | `execute` | 전부 |
| 그 밖의 모든 동료 | `read` | 읽기, 그리고 메시로 답하기 |

동료가 무엇을 말하든 기본값은 `read` 다. 올라가는 길은 하나뿐이다 — **내가 설정 파일에 그 사람 지문을 적을 때.** 채팅으로 부탁해서 올라가지 않고, 모델이 설득당해서 올라가지도 않는다.

```jsonc
// ~/.agent-channel-mesh/config.json
{
  "self": ["1bba b23d b269 4e47 b0ca 42be c05f 7f3b"],   // 내 다른 에이전트의 지문
  "policy": {
    "default": "read",                                    // 생략하면 read
    "peers": {
      "3f0c 91a2 …": "write"                              // 이 동료만 편집까지
    }
  }
}
```

**키는 라벨이 아니라 지문이다.** 라벨은 화면에 보려고 적는 표시용 문자열이라 아무 값이나 될 수 있다. 지문은 `whoami` 툴이 보여주고, 3단계에서 대조한 바로 그 값이다.

### 무엇이 막히나

동료의 말이 세션에 들어와 있는 동안, 그 권한을 넘는 툴 호출이 거부된다.

| 등급 | 되는 것 | 안 되는 것 |
|---|---|---|
| `read` | 파일 읽기·검색, 메시로 답하기 | 편집, 명령 실행, 웹 요청, 다른 MCP 툴 |
| `write` | 위 + 파일 편집 | 명령 실행, 웹 요청, 다른 MCP 툴 |
| `execute` | 전부 | — |

분류에 없는 툴은 전부 `execute` 로 친다. 툴은 계속 늘어나므로 목록이 항상 뒤처지고, 뒤처진 자리가 통과 쪽으로 떨어지면 새 툴이 그대로 우회로가 된다.

### 막혔을 때

**한 줄 입력하면 풀린다.** 사용자가 직접 친 것이 "이 일은 내가 시켰다"의 유일한 신호이기 때문이다. 거부 문구에 누가 무엇 때문에 막혔는지 들어 있으니, 에이전트가 그것을 옮겨 말하면 무엇을 승인하는지 알고 승인하게 된다.

시간이 지난다고 풀리지는 않는다 — 그 말은 여전히 컨텍스트에 있다. 그래서 동료 메시지가 턴 도중에 도착하면 **그 턴의 남은 편집이 막힐 수 있다.** 불편하지만 그대로 둔다. 그 말이 들어온 뒤의 행동이 그것 때문인지 아닌지 구분할 방법이 없기 때문이다.

### 막지 못하는 것

**정보가 나가는 것은 막지 못한다.** 읽고 답할 수 있다는 것이 곧, 모델이 도착한 말에 실린 지시를 따라 아는 것을 말해 버릴 수 있다는 뜻이다. 이 경계가 지키는 것은 **내 호스트를 바꾸는 일과 명령을 돌리는 일**이며, 그 이상을 주장하지 않는다.

민감한 저장소에서 일하는 세션은 채널에 붙이지 않는 것이 유일하게 확실한 방법이다. 자세한 설계 근거는 [docs/architecture.md §8](docs/architecture.md).

## 플러그인 없이 붙이기 (개발용)

이 레포를 고치면서 그 자리에서 시험할 때는 커밋된 번들이 아니라 작업 트리를 물려야 한다. 사용자용 경로가 아니다.

```bash
claude mcp add agent-channel-mesh -- bun run "$PWD/src/adapter/bin.ts" --delivery both
codex  mcp add agent-channel-mesh -- bun run "$PWD/src/adapter/bin.ts" --delivery inbox

bun run src/install/hooks.ts
```

`--delivery` 는 필수다. 환경을 보고 추측하면 틀렸을 때 조용히 틀린다 — Claude 에서 수신함 모드로 뜨면 메시지가 도착해도 세션은 영원히 모르고, Codex 에서 주입 모드로 뜨면 선언한 capability 를 아무도 구현하지 않는다.

훅 설치기는 두 에이전트의 `hooks.json` 을 함께 쓴다. 신원을 갈랐다면 각자의 설정을 지정한다 — 두 에이전트에 같은 경로를 주면 거부한다.

```bash
bun run src/install/hooks.ts \
  --claude-config ~/.agent-channel-mesh/config.json \
  --codex-config  ~/.agent-channel-mesh/codex.json
```

플러그인 산출물(매니페스트·훅)은 손으로 고치지 않는다. 생성기를 고치고 다시 뽑는다.

```bash
bun run plugin
bun test
```

## 배포

상시 릴레이는 서버리스 함수로 올린다. 상시 구동 서버가 필요 없고, 릴레이가 하는 일이 암호문을 잠깐 보관했다 넘겨주는 것뿐이라 그 모델에 맞는다.

**저장소는 반드시 외부여야 한다.** 서버리스는 요청마다 다른 인스턴스에서 실행될 수 있어, `POST /post` 를 처리한 인스턴스와 `GET /fetch` 를 처리한 인스턴스가 다르면 메모리에 담은 봉투가 사라진다. 테스트는 통과하는데 실제로는 메시지가 없어지는 고장이다.

### Vercel + Upstash

```bash
vercel link                                    # 프로젝트를 연결한다
vercel env add UPSTASH_REDIS_REST_URL          # Upstash 콘솔의 REST URL
vercel env add UPSTASH_REDIS_REST_TOKEN        # 같은 화면의 REST 토큰
vercel env add CRON_SECRET                     # 임의의 16자 이상 문자열
vercel env add ACM_RELAY_TOKEN                  # openssl rand -hex 32 — 참여자에게 나눠 준다
vercel deploy --prod
```

배포판이 실행하는 것은 로컬과 **같은 파일**(`src/server.ts`)이고, 라우팅도 같은 핸들러가 한다 — 라우팅을 배포용으로 다시 만들면 두 경로의 동작이 갈리고 그 차이는 배포한 뒤에야 드러난다. 다른 것은 저장소뿐이다: 자격이 있으면 Upstash, 없으면 메모리이며, **서버리스에서 자격이 없으면 기동 시 죽는다**(인스턴스마다 메모리가 갈려 봉투가 조용히 사라지므로).

`ACM_RELAY_TOKEN` 도 마찬가지로 서버리스에서는 없으면 죽는다. 배포된 릴레이는 누구나 닿는 공개 주소이고, 주소를 우리가 고르지도 못하기 때문이다.

> **신규 프로젝트의 첫 배포는 preview 로 요청해도 production 이 된다.** 승격할 production 이 아직 없기 때문이다. "preview 니까 안전하다"고 가정하면 안 된다 — 환경변수를 먼저 넣고 배포한다.

붙었는지 확인한다.

```bash
curl https://<배포주소>/health          # {"ok":true}
```

### 30일 아카이브 방지

Upstash 무료 티어는 **30일 동안 명령이 하나도 없으면 DB 를 아카이브**한다 — 인스턴스가 제거되고 REST 엔드포인트가 죽는다. 다시 만들 수는 있지만 URL 과 토큰이 새 값이라 환경변수를 갈아끼우고 재배포해야 하고, 무엇보다 **조용히 일어나서** 릴레이가 실패하기 시작한 뒤에야 알게 된다.

`vercel.json` 의 Cron 이 주 1회 `GET /keepalive` 를 쳐서 그 타이머를 리셋한다. `/health` 로는 안 된다 — Redis 에 닿지 않아 명령이 발생하지 않는다.

이 경로는 **저장소가 Upstash 일 때만 존재한다.** 메모리 저장소로 뜬 릴레이에서는 404 다 — 아무 데도 닿지 않으면서 `ok:true` 를 돌려주면 cron 은 성공을 보고 아카이브는 그대로 진행되기 때문이다.

**`CRON_SECRET` 은 선택이 아니다.** Vercel 은 cron 요청에 인증을 자동으로 붙이지 않는다 — 이 값을 설정하면 `Authorization` 헤더로 실어 보낼 뿐이고, 검증은 엔드포인트가 한다. 설정하지 않으면 `/keepalive` 는 500 을 돌려주며 아무 일도 하지 않는다. 조용히 공개 엔드포인트가 되는 것보다 낫다.

Cron 스케줄의 **타임존은 항상 UTC** 다. `0 21 * * 0` 은 일요일 21:00 UTC — 한국시간으로 월요일 06:00 이다.

### 올리기 전에

배포하면 공개 주소가 생긴다. 수신함 폴링은 서명으로 인증되므로 남이 내 큐를 비울 수 없지만, **채널에 쓰는 것은 채널 비밀만으로 된다** — 비밀을 누구에게 줬는지가 유일한 통제 수단이다. 아래 **보호하는 것과 하지 않는 것**을 읽고 올린다.

## 보호하는 것과 하지 않는 것

"종단 간 암호화"가 실제보다 많은 것을 약속하지 않도록 경계를 밝힌다.

**보호한다**
- 메시지 **내용**. 릴레이는 복호화할 수 없다.
- 발신자 유출에 대한 순방향 비밀성 — 메시지마다 새 임시 키를 쓴다.

**보호하지 않는다**
- **메타데이터.** 릴레이는 누가 누구에게, 언제, 얼마나 자주, 얼마나 크게 보내는지 본다. 소셜 그래프와 활동 패턴이 노출된다.
- **폴링하는 사람의 신원.** 수신함 폴링은 서명 공개키를 릴레이에 넘기므로, 릴레이는 그 키의 지문(§9)을 계산할 수 있다 — key id 8바이트만 보던 때보다 정밀한 식별자다. 서명으로 인증하는 이상 피할 수 없다: 검증하려면 검증키가 있어야 한다. 메시지 내용에는 여전히 닿지 못한다.
- **시간 창 안의 요청 재생.** 릴레이는 무상태라 이미 본 요청을 기억하지 못한다. 그래서 유효 창(5분) 안에 캡처된 폴링 요청은 그대로 재생될 수 있다. 캡처 자체를 막는 것은 TLS 이고, 그건 이 인증이 주는 성질이 아니다.
- **도착한 말에 실린 지시에 모델이 따르는 것.** 권한 경계는 **호스트 변경과 명령 실행**을 막지, 모델이 아는 것을 말하는 것은 막지 못한다 — 읽고 답할 수 있다는 성질이 곧 그 통로다. [권한](#권한--도착한-말이-내-기계에서-무엇까지-하나) 참조.
- **수신자 키 유출에 대한 순방향 비밀성.** HPKE(RFC 9180)는 어떤 모드에서도 이를 제공하지 않는다. 공격자가 장기 개인키를 훔치고 트래픽을 녹음해 뒀다면 전체 이력을 복호화한다. Double Ratchet 을 쓰지 않는 근거는 [docs/architecture.md §10.4](docs/architecture.md) 에 있다.

**릴레이의 상태**
릴레이는 **논리적으로 무상태**다 — 장기 프로세스를 돌리지 않고 세션·래칫·그룹 상태를 갖지 않는다. 다만 오프라인 전달을 위해 암호화된 blob 을 TTL 저장소에 보관한다. 그 내용은 읽을 수 없다.

**수신함은 서명으로 인증된다**
폴링 요청은 **두 공개키**(KEM·서명)와 서명을 함께 싣고, 릴레이는 `key id == keyIdOf(KEM 공개키, 서명 공개키)` 와 서명·시각만 확인한다. key id 가 두 키를 함께 해시한 값이라, 제시된 서명키가 그 큐 주인의 것임이 key id 계산만으로 증명된다 — 릴레이가 매핑을 저장하지 않아도 되는 이유이고, 남의 KEM 공개키를 아는 채널 동료조차 자기 서명키를 붙여 남의 큐를 비울 수 없는 이유다. 자세한 것은 [docs/architecture.md](docs/architecture.md) §10.12.

**봉투를 올리려면 릴레이 토큰이 필요하다**
공개 주소로 뜬 릴레이는 `Authorization: Bearer` 를 요구한다. 막는 것은 기밀이 아니라 가용성이다 — 아무나 올릴 수 있으면 남의 수신함을 쓰레기로 채워 **아직 못 받은 진짜 메시지를 큐 밖으로 밀어낼 수 있다.** 이 토큰은 배포 단위이고 **채널 접근 제어가 아니다** — 토큰을 가진 쪽도 아무 채널에나 올릴 수 있으며, 그것을 막는 것은 수신자의 검증이다. 자세한 것은 [docs/architecture.md](docs/architecture.md) §10.13.

**로컬에는 평문이 남는다**
릴레이는 읽지 못하고 7일 뒤 지우지만, 받은 쪽의 로컬 저장소에는 복호화된 대화가 남는다 — 그래야 밀린 메시지를 종합해 보고하고(§6.1) 지난 대화를 볼 수 있다. 파일 권한은 `0600` 이고, 보관 기한과 채널 단위 삭제를 사용자가 정한다. 자세한 것은 [docs/architecture.md](docs/architecture.md) §6.3 · §10.14.

## 요구 사항

- [Bun](https://bun.sh) — 훅과 어댑터가 `bun` 으로 뜬다. 그 밖에 깔 것은 없다 — 의존성은 플러그인 번들 안에 들어 있다.
- Claude Code 또는 Codex. 둘 다 **플러그인과 훅을 지원하는 버전**이어야 한다 — 훅이 없으면 도착 알림이 없고, 툴은 붙었는데 아무도 말을 걸지 않는 상태가 된다.
- 채널 주입(Claude 의 즉시 도착)은 `--dangerously-load-development-channels` 에 걸린 실험 기능이다. 없어도 훅과 수신함으로 동작한다.
